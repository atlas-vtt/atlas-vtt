# Context
- We are working on Atlas VTT, a Virtual Tabletop plugin for Obsidian.md
- **IMPORTANT**: We use PIXI.js v8 (not v7). Obsidian bundles PIXI v7 globally, but we must use our own PIXI v8 imports.

# Coding pattern preferences
- Adhere to the single responsibility principle SOC
- always prefer best practice solutions
- Avoid duplication of code whenever possible, which means checking for
other areas of the codebase that might already have similar code and
functionality
- Before you code anything with PixiJS or alter Pixi code always check online first if you are adhering to the newest pixiJS V8 best practices.
- If you believe that you would benefit from up to date information on some framework when e.g fixing a warning about PixiJS v8, please just use web search without asking.
- You are careful to only make changes that are requested or you are
confident are well understood and related to the change being requested
- When fixing an issue or bug, do not introduce a new pattern or
technology without first exhausting all options for the existing
implementation. And if you finally do this, make sure to remove the old
ipmlementation afterwards so we don't have duplicate logic.
- Keep the codebase very clean and organized
- Avoid writing scripts in files if possible, egpecially if the script
is likely only to be run once
- Avoid having files over 200-300 lines of code. Refactor at that point.
- Mocking data is only needed for actual test files, never mock data otherwise
- Never add stubbing or fake data patterns to code 
- In Typescript always type out return types in functions to make onboarding new team members easier and to provide clearer intentions 
- Prefer SCSS classes and Obsidian native styles (see obsidian-colors.md). Tailwind utilities exist in older components and are scoped under `.atlas-vtt-plugin`; do not add new Tailwind usage.

# UI Design Principles
- **Uniform padding**: Every container must use equal padding on all sides and the same value for gaps between child elements. A tooltip, modal, or toolbar with `padding: 8px` must also use `gap: 8px` between its children. Never use asymmetric padding (e.g. `6px 12px`) unless there is an explicit, justified reason.
- **Consistent stroke/border style**: All elevated surfaces (toolbars, tooltips, modals, popovers) share the same border treatment defined in the `atlas-elevated-surface` mixin (`styles/_mixins.scss`). Use it instead of ad-hoc border values.
- **Nested border radius**: The mathematical formula is `inner = outer - padding`, but this only matters when elements are flush against the container edge. For elements separated by padding (buttons inside panels), step down one level in the radius scale instead: containers use `$radius-xl` (12px), inner elements use `$radius-l` (8px). Both look clearly rounded and the padding gap prevents the eye from comparing curves directly.
- **Close buttons**: every panel closes with `CloseButton` (Obsidian modals opened by Atlas add `ATLAS_NATIVE_MODAL_CLASSES` to `modalEl`). The panel sets its corner with `atlas-panel-radius($radius-2xl)` and its header with `atlas-close-header`, so the button sits `$close-button-gap` from the border with a concentric corner. Concentric means outer = inner + gap, and only on the corners that face the panel's corners: a small element keeps the control radius on its other corners, or its edges curve away from the panel's and the gap stops being even. When the inner radius comes out near 0, the panel's radius is too small, so raise it; never shrink the inner one. Elements near such a panel's corners use `atlas-panel-inset-radius($inset)`.
- **One corner language**: every floating surface (dialogs, panels, the toolbar and undo/redo bar, scene tab bar, widgets, initiative trackers, dice tray, toolbar dropdowns) uses `atlas-panel-radius($radius-2xl)` with its corner controls $spacing-s inside the border; context menus are tighter: their rows are 28px capsules $spacing-xs inside the border, all rounded alike, and the menu's corner is derived from them so every row stays concentric (`atlas-context-menu.scss`); bars shorter than 48px render as capsules, so their end controls cap the inset radius at half their height (`atlas-panel-inset-radius-value($inset, $max)`). Surfaces and inset elements also take Obsidian's `corner-shape` (`atlas-corner-shape`, a superellipse on macOS): Obsidian gives every `<button>` that shape, and a squircle inside a round corner never keeps an even gap. Panels built with the DOM instead of React open and close with `animatePanelIn` / `animatePanelOutAndRemove` (`src/app/ui/panelMotion.ts`), the same motion as the dialogs.
- **No native tooltips**: never set a `title` attribute (browser tooltip; a lint rule rejects it). Obsidian's `aria-label` tooltip is switched off on every element with an `atlas-` class and its subtree (`styles/_native-tooltips.scss`), so `aria-label` only names controls for screen readers. Show a tooltip only where it is wanted, with `LabelTooltip`. The one rich tooltip is the toolbar editor's card (`ToolbarEditTooltip`): it is no Radix layer, hides at once on any keydown (and any press, wheel, context menu or drag) and never prevents Escape, so the same press goes on to whoever uses it. A showing tooltip takes Escape first and prevents its default, so whoever leaves a key alone that a control used asks `handledByAnotherControl` (`keyboard/tooltipEscape.ts`), which does not count the tooltip's own dismissal. It does count it while a list the key belongs to is open (a select's options, a menu): the list the key was pressed in, one inside the popover or dialog that holds the key's target (`[role="dialog"]`, `.atlas-modal`, Obsidian's `.modal`), or one a control in there has open in a portal (`aria-expanded` with `aria-controls`); lists anywhere else in the document are not looked at. A listbox that always stands open (search results, a picker's choices) carries `STANDING_LIST`, since Escape is never its own.
- **Main toolbar** (`packages/components/toolbar/`, `src/app/toolbar/`): every control is described once, in `toolbarCatalog.ts` (pure, read by `SettingsService`: id, label, the editor's one-sentence description, hotkey, `dmOnly`, `enabled` / `experimental` gates, the default order) and by its item in `toolbarControls.tsx` (keyed by catalog id); a new control also needs a screenshot in `toolbarScreenshots.ts` (560 × 350 WebP, at most 40 KB: `tests/unit/toolbarScreenshots.test.ts`, since the build inlines them into `main.js`). The catalog label names a control only in the editor; its button keeps its own label and tooltip. The GM's layout is `AtlasSettings.toolbar` (`toolbarLayout.ts`: one order over all controls plus a hidden list, only what differs from the default, ids of newer versions kept; a hidden undo/redo bar is `UNDO_BAR_ID` (`undo`) in the hidden list and never in the order); a hidden control keeps its place and its hotkey, and visits that place once it becomes active while hidden (`nextVisitArmed`), never while the editor is open. The Command palette control can never be hidden. The player view's bar ignores the layout. `BottomToolbarRow` centres the bar and tells it its width; controls that do not fit move into the "More tools" menu from the right (`toolbarFit.ts`), pinned ones (active tool, a control whose menu or panel hangs from it, the Command palette) never. The GM view switch is `ResponsiveToolbar`'s `end` control: always shown, always last, after "More tools", and not part of the editor. Hidden and overflowed controls stay mounted with `hidden`, so keep tool option state in the group components. The bar's own rules are scoped to `.atlas-main-toolbar`, since the undo/redo bar shares `.atlas-vtt-toolbar`. "More tools" closes on Escape in the capture phase and prevents its default. Popovers keep inside their view with `useKeepInView` and the `atlas-keep-in-view` mixin.
- **Toolbar editor** (`packages/components/toolbar/editor/`): the GM arranges the bar from the command palette (Customize toolbar; `isToolbarEditing` in the UI slice, never saved). Done, an Escape no control used, a left press outside the bars, the tray and the editor's menu (the press still does what it does there; `EDITOR_SURFACES` in `ToolbarEditor.tsx`), another tab coming to the front and the map unloading end it, and opening the palette, the dice tray or the asset manager ends it first (the rule is in the store setters). The tools are inert while it lasts, each over a handle button (`ToolbarItemHandle`): a drag reorders the bar or hides a tool into the tray above it, a right-click offers Hide or Show on toolbar, and the keyboard does all of it (arrows move focus, Alt with them moves a tool, Delete hides, Enter shows, Shift+F10 opens the menu; Tab, Space, Enter, Delete and Backspace never reach the map's shortcuts from any control of the editor, during a drag too, or Delete on a tray tool deletes the map's selection); `ToolbarLiveRegion` says what changed. `ContextMenuProvider` opens its menus in the document it renders in, so a map in a popout gets them there, and a menu opened from the keyboard names where focus returns (`returnFocus`), since its trigger is a point that cannot hold focus. The tray, the card and the ghost layer are absolute children of the bottom row, never of the bar (the editor's grid area names all four lines, since an absolutely positioned grid child's `auto` line is the row's edge; the ghost layer spans the whole row), so the bar's end radii and the row's width measurement stay untouched. Slots open and close their real width (`useSlotPresence`; `data-animating` keeps them out of `measureBar`), the tray keeps a slot for every control, and `layout="position"` glides only when the stored layout changes, also from another view (`useLayoutMotion`'s revision), so visits and resizes snap. A drag captures the pointer on the bar once it passes the threshold (before that a Ctrl+click or long press must still send its context menu to the handle) and takes its moves and release on the window in the capture phase, so the map never sees them (`toolbarPointerSession.ts`); its state is per toolbar (`toolbarEditStore`, whose `frozenLayout` keeps the bar still under the pointer: changes from elsewhere wait for the drop), and the drop index reads the bar's resting layout (`settledBar`, `toolbarDropIndex.ts`). Await a Motion animation only through a `.then` called at once (`run` in `dragGhostMotion.ts`): one that ends in the same tick replaces its finished promise. The card over a tool (`ToolbarEditTooltip`, `useEditTooltip`) opens after 500 ms of hover or at once for keyboard focus, hangs above the tray, glides between neighbours, leaves out its screenshot where the room above the tray is too low, and gives touch none. The undo/redo bar is one more hideable unit (`UNDO_BAR` in `toolbarCatalog.ts`, `ToolbarUnitId`): its own bar in `BottomToolbarRow`'s start slot (`UndoBarSlot`), never part of the main bar's order, never reordered and never dropped into the bar (dropped anywhere over the bar or its own place it settles back there; the bar opens no well for it). The editor lives in MainToolbar, so `BottomToolbarRow` shares it through `ToolbarRowBridge` (the row's edit store, and the editor's api MainToolbar publishes after each render), and the bar takes a handle over its whole surface while editing; its handle is the first of the bar's group for the arrow keys. Hidden, it stays mounted (its hotkeys keep working), its place takes no room (the main bar's fit gets it), and it is the tray's first face; during its drag its place stays open, since a change of the row's room cancels a drag. `tests/gpu/toolbarEditor*.gpu.test.ts` measure placement, corners, drags (the undo/redo bar's too) and the card in a real layout.
- **What the Atlas VTT theme leans on** (`~/Github/atlas-vtt-theme`, in Obsidian's theme directory): it grows ivy over the corners of the statblock previews, the asset manager and the command palette with pseudo-elements of `.atlas-statblock-preview-window`, `.statblock-hover-preview`, `.atlas-asset-manager-window` and `.atlas-command-palette-window`, placed by the preview's `$spacing-s` inset around its card and the asset manager's `$spacing-2xl` margin. `.atlas-asset-manager-window` and `.atlas-command-palette-window` are the elements framer-motion moves and fades; they must not clip, and their pseudo-elements must stay free (the container inside each clips and lays out), or the ivy stops moving with its panel. It sets statblock headings (`.atlas-sb-heading`, `.atlas-sb-section-heading`) and the name of a roll (`.atlas-dice-roll__label`, `.atlas-dice-toast__ability`) in its heading face. Changing any of these, look at the theme. A theme asks previews for room at the window's edges with `--atlas-statblock-preview-gap-block` / `-inline` on `body` (`statblock/previewEdgeGap.ts`), which both preview kinds honour.
- **Reuse shared components**: Toolbar buttons must use the `ToolButton` component. Don't create custom button markup/classes that duplicate what `ToolButton` + `Button` already provide.
- **Tool menus** (`toolbar/*ToolGroup.tsx`): choices are `DropdownMenuItem` rows with a tick (and the tool's shortcut), a switch is a `DropdownToggleRow` (`ToggleSwitch`: `role="switch"`, Space and Enter, named by the row's text), mixed controls and actions get their own `atlas-dropdown-section`. A menu has one text edge, `--atlas-menu-text-inset` (where its rows' content begins): switch labels, slider names and values (`DropdownSliderRow`) and section labels (`atlas-dropdown-label`, the swatch grid's label) start on it, while tracks, grids and segmented controls span the menu. Rows take the menu's inset radius; a `SegmentedControl` in a menu is one row, with its options concentric inside the track (`dropdown-menu.scss`). The toolbar's blanket button rules (`main.scss`) reach into the menus that hang from it: they skip `$own-look` (the dice tray, segmented options), and the tool group's own reset stops at its two buttons. A menu keeps its shape: what a switch in it turns off stays in place and is shown disabled (`disabled` on `DropdownMenuItem`, `SegmentedControl`, `DropdownSliderRow`), never removed, so the switch does not move under the pointer (the lighting menu while dynamic lighting is off; `tests/gpu/lightingMenuShape.gpu.test.ts` measures it). A toggle's radii come from the scale (`$radius-xl` switch, `$radius-l` thumb); its corners that face a panel's or the bar's corner are set on `.atlas-toggle`.

# Memory Notes

## Successfully Hiding Obsidian Tabs for Note Preview
To hide tabs while maintaining full editing functionality in the note preview window:

1. **CSS Approach**: Add styles to hide tab headers with a specific data attribute:
   ```css
   .workspace-tab-header[data-atlas-preview="true"] {
     display: none !important;
   }
   .workspace-tab-container:has(.workspace-tab-header[data-atlas-preview="true"]):not(:has(.workspace-tab-header:not([data-atlas-preview="true"]))) {
     display: none !important;
   }
   ```

2. **Leaf Management**: 
   - Create a new leaf with `this.app.workspace.getLeaf(true)`
   - Mark the leaf and its tab header with `data-atlas-preview="true"` attribute
   - **Critical**: Call `leaf.detach()` to remove the leaf from the main workspace split
   - This prevents the leaf from affecting the active view while keeping it functional

3. **View Preservation**:
   - Store the original active leaf before creating the preview leaf
   - After opening the file in the preview leaf, restore the original active leaf
   - Use `this.app.workspace.setActiveLeaf(originalActiveLeaf, { focus: false })`

4. **Content Rendering**:
   - After detaching, manually append the leaf's view container to the preview window
   - This maintains full editing capabilities while preventing workspace navigation

This approach ensures the user stays on the map canvas while previewing notes with full editing support.

## Hexagonal Grids
Hex geometry lives in `src/app/grid/hexGeometry.ts` and rendering in `src/app/grid/hexGridDrawer.ts`.

- **Size convention**: `grid.size` is the flat-to-flat distance of a hex (width of a pointy-top hex, height of a flat-top hex), the same convention Foundry VTT and Owlbear Rodeo use. Circumradius is `size / sqrt(3)`. A size-1 token therefore has the same pixel diameter on hex and square grids.
- **Orientation**: `hex-vertical` = pointy-top (rows), `hex-horizontal` = flat-top (columns).
- **Coordinates**: axial `(q, r)` with cube rounding for pixel-to-hex (Red Blob Games). Never round `q` and `r` independently.
- **Origin**: `(offsetX, offsetY)` is the top-left of hex `(0, 0)`'s bounding box, so a hex map whose first hex is flush with the image corner aligns at offset 0.
- **Drawing**: each row/column emits one zig-zag polyline plus one straight edge per hex, so every edge is drawn exactly once (no edge deduplication, no double-drawn lines). The `Graphics` is drawn in world space and clipped by a map-sized mask; do not bake it into a texture (that introduced sub-pixel offsets in the past).
- **Distance**: hex steps via `axialDistance`; square grids use Chebyshev distance.
- **Dotted style**: vertex markers are single filled polygons (`drawVertexMarker`), never overlapping strokes, so the centre stays crisp at any opacity. The `GridSystem` fills for dotted and strokes otherwise.
- **Linked hexes**: a `NotePin` with `hex: true` links its note to the hex containing its point (`grid/hexLinks.ts`), so a realigned grid keeps it on the same part of the map; on non-hex grids it falls back to a pin. At rest it shows only its pin, which `PinRenderer` draws in the centre of the hex (`pinDisplayPoint`) but never hit-tests. `HexLinkRenderer` draws the hover, press and Shift-preview highlight (DM-only, above the lighting, `MAP_LAYER_Z.hexLinks`) and `HexLinkInteraction` handles hover, click-to-open (the press stays unhandled so drags still pan) and the context menu, dispatched from `TokenRenderer` for the select and move tools. The Note Pin tool links with Shift (`tools/notePinPreview.ts`); a hex holds one note.
- **Alignment**: on hex grids each measurement is one hex edge (two neighbouring corners); `hexAlignmentMath.ts` detects orientation from edge angles, seeds the lattice from the first edge, and fuses further edges with a beam search over lattice-vertex assignments plus least squares. Two edges along one axis are inherently scale-ambiguous; a third edge in another direction resolves it, so the 4-quadrant flow is the precise one.
- **Auto-detect**: `src/app/pixi/gridDetection/` works as propose, fit, verify. *Propose*: the power spectrum of the map's line contrast (square = axis peaks, hex = six peaks at 30°+k·60° pointy / k·60° flat) is summed over harmonics, because thin lines are a comb whose fundamental is its weakest peak on textured art; two views propose (contrast before and after downsampling, for thin and thick lines). The spectrum never decides anything. *Fit*: `edgeProfile.ts` averages the image along each cell edge before rectifying, so faint lines add up coherently; `latticeSearch.ts` profiles ~800 edges once and scores every nearby size/offset by reading those profiles (one vote per edge, so heavy ink cannot outvote a faint grid); `latticeFit.ts` then measures each edge's sub-pixel distance to its line and solves size and offset in one robust least-squares (distances are linear in the three unknowns because every grid point is `origin + size * latticeCoordinate`; Tukey weights with a shrinking cutoff drop hidden edges and map art). Edges come from the real drawers via `gridTemplate.ts`, so detection and rendering cannot disagree. *Verify*: `support` is the chance-corrected share of edges with a line within 0.75 px, taken over the weakest edge direction (another grid type can share one direction's lines, never all); below 0.05 the map has no grid and the manual tool is the fallback. Size multiples are compared at equal edge length (longer edges see fainter lines) and the smallest within 75% of the best wins. Size changes scale about the image centre. Mind the half-pixel convention: detected pixel indices get `+0.5` before becoming world coordinates.

## Cell Numbering
Numbering is grid-type-agnostic, behind a `CellLattice` seam (`src/app/grid/cellNumbering.ts`): `numberCells` and the three formats it offers are pure functions of a lattice and a map rect, shared by hex and square grids alike.

- **Formats**: `column-row` ("0304": column 3, row 4, each part padded to the widest number present, minimum 2 digits), `sequential` (1, 2, 3 in reading order: sort by row then column), and `letter-number` (A1, B1, ... AA1: a bijective base-26 column letter, unpadded row number). All three are offered on every grid type.
- **Membership**: a cell counts when its centre lies at least `EDGE_MARGIN` (0.4) × size inside every map edge, so a cell the map edge cuts in half gets no number.
- **Lattices**: `hexLattice.ts` (axial coordinates, keyed by `axialKey`) and `squareLattice.ts` (integer column/row, no stagger) each implement `CellLattice.cellsOnMap`. On a hex grid each column (flat-top) or row (pointy-top) counts from its first whole hex, which absorbs the half-cell stagger; squares have no stagger, so the same formula degenerates to counting from the first on-map column/row.
- **Persistence**: `GridState.cellNumbers` / `cellNumberOpacity` (`services/MapPersistence.ts`); `migrateGrid` reads the older `hexNumbers` / `hexNumberOpacity` keys from maps saved before square grids could be numbered (a file holding both keeps the new one).
- **Rendering**: `GridSystem` builds a `CellLattice` for whichever grid type is active and draws the labels with `CellNumberLabels` (`cellNumberLabels.ts`) as `BitmapText` in the grid container, so they share its mask, alignment moves and player-view visibility, and hide while too small to read. The digit atlases are built without mipmaps at power-of-two sizes, and labels switch to the smallest atlas at least as large as they appear on screen: any mip level or a larger downscale blurs them.
- **Hex links**: `HexLinkRenderer.numberOf` looks a hex's number up by `axialKey`, the hex lattice's own key spelling — keep it that way so the hex-link chip's number and the grid's numbering can never diverge. Square grids have no linked cells (see "Linked hexes" above).

## Vault files and the asset index
The library lives in visible vault files, so every sync tool carries it (Obsidian Sync, Remotely Save and Self-hosted LiveSync skip dot folders, Remotely Save also names starting with `_`); the asset index (`atlas-vtt/.atlas-data/assets-metadata.json`) is only this device's cache of them and must follow the vault, including changes made outside Atlas (file explorer, file manager, sync tools, git). Plan: `docs/plans/2026-10-04-atlas-synced-library-data.md`.

- **Three kinds of data, three places**: content and library facts in vault files; the GM's preferences in the plugin's `data.json` (`SettingsService`, followed through `onExternalSettingsChange`; a change made here and not yet saved survives a reload, and reading never rewrites it, since devices on other versions share it: hotkeys equal to this version's default are written back as they were); facts about one device (input mode, crash marker, migration flags, device id) in `app.saveLocalStorage`. The old settings file records the presets that became files (`systemPresetsMovedIds`), so no device brings back a preset deleted since, while one an older Atlas added later still moves; migrated preset files carry a piece of their id in the name, since devices migrating at once would otherwise write one name, of which sync keeps one. A reload that reads no settings record (a file a sync tool is still writing) keeps the settings. Where a setting is shown is independent of where it is stored. Anything new that persists picks one of the three; never library data in the index alone.
- **Library files** (`services/library/`): every asset has a record file holding its whole record (`recordFile.ts`): the JSON of maps, scenes, encounters and the other JSON-backed types keeps its payload at the top level, as older versions read it, with the record beside it under `atlasRecord` (format, fields, and the collection it was written for); tokens and notes have `tokens/<id>.json` / `notes/<id>.json` (`recordFilePath`). A collection's record (settings, tags, release) is `collection.json` in its folder, without id and name (the folder's); `library.json` holds `defaultCollectionId`, `vaultId` and `starterTokensAdded`. A record with a higher format is read and never rewritten.
- **Writing** (`LibraryWriter`): every save of the index writes the library files whose content changed since this device last read or wrote them (stamps in the cache's `libraryState`), then the cache; a save takes the index as it is when its turn comes, never as it was when asked for. A file that vanished since it was seen is never written back (the vault check decides), a record whose collection changed is moved, the old file of a moved record goes only once the new one is written, files of records that left the index are trashed, and a failed file is reported and tried again; a failed import or transfer puts the files back (`rollBackTo`). Nothing is written before the files were read once.
- **Reading** (`readLibraryChanges`, `mergeLibraryChanges`): the vault check and `refreshMetadata` read the library files that changed (by size and time, then content) and their content wins over the index; vault `modify` events on library files schedule the check, and changed collection settings reach open maps through `atlas-vtt:collection-settings-changed`. A record whose file is gone leaves the index, and comes back with the file (an evicted iCloud file, a sync in flight). Where several files hold one id (`recordHolders.ts`), the choice comes from the files alone, so every device makes the same: files written for the folder they lie in are versions of one record (a conflict copy, a move racing an edit) and one named for the record wins, then the newest edit, then the first path, the others left alone; files written for another collection came with a copied folder and become records of their own (`copyId`, paths into the old folder follow). A `collection.json` carrying the uid of a collection whose own file is gone is that collection's folder renamed outside Obsidian; one whose original is still there is a copy and gets a uid derived from the original's, written to its file. A copy is taken in only once it has stood `COPY_SETTLE_MS` beside its original (`settledCopy`, the check runs again then): a sync tool may deliver another device's rename as the new folder first and the old one's deletion later, which within that time reads as the move it is. `libraryClock` lets tests move time on.
- **Derived records**: what Atlas works out by itself is never written until the user changes it, recognised by what it is, never by when it appeared (a user edit made during a check is always written): a record adopted from a file no record owned (a recovered id, `LibraryState.derived` with its content's hash; from an older version only while `modifiedAt` equals `createdAt`), a collection exactly as `derivedCollectionRecord` makes it for its folder, and a library whose only fact is the first collection as default (`DesiredFile.derivable`). Every device works out the same. Such a record is never written over a file this device has not taken in (a copy still waiting). The publisher id is made only when first needed (`getVaultId`; comparisons use `knownVaultId`), and starter tokens have fixed ids and wait for the first vault check (`vaultChecked`), so a device that starts before sync delivered the library writes nothing over it. A derived collection's uid is the same in every vault, so an export first gives it one of its own (`ensureOwnCollectionUid`).
- **A token, map or scene whose record file this device knows** goes only with that file, never because its art or map is missing or was seen deleted: a sync tool may deliver the record before its art, or another device's rename as a deletion and a creation, and a device cannot tell either from the user deleting the file. Deleting art or a map outside Atlas leaves its record with a missing file; Atlas' own delete removes both. Without a known record file the old rule holds. For the same reason the vault check never trashes snapshots; the device that deletes a scene does, and a scene that changed collection outside Atlas takes its snapshots along (`followSceneSnapshots`).
- **Migration** runs per device and is recorded in local storage, never in a synced file: the first check after loading writes every record, collection and library file the vault lacks. Until then each device's index was its own copy of the library, so a record or collection file wins over the index entry only when its `modifiedAt` is newer, and an older version's payload file never wins over a payload the index holds (older versions rewrote encounter token refs in the index alone, after an art rename without touching `modifiedAt`, so no time tells a stale file from a newer one; another device's edit arrives as its record file once that device migrated, where the later edit wins, a tie keeping the index). Known limit: where two devices both changed one encounter's token list on older versions, the later stamp wins whole. Once migrated, files win. A token an older version rebuilt from art (a recovered id) that a real record now owns is dropped; what the user did with it passes to that record (`passEdits`: a name its file does not give, tags, fields rebuilding never sets, the later edit winning) and encounters name the record instead (`dropShadowedRecoveries`). The earliest data migration (`runStartupMigration`, visible files into `.atlas-data`) never runs in a vault that has `library.json`: a joining device would hide synced files, and sync delete them elsewhere. The visible index of older versions (`atlas-vtt/assets-metadata.json`) is read only while no `library.json` exists and is trashed once this device has written the library. Install records move from `.atlas-data/installs/` into the collection folder (`install.json`, `migrateInstallRecords`; where another device moved its record first, the later install stays); a map JSON matching an older record's fingerprint taken with its collection counts as unchanged (`installedFileHash`); `readInstallRecord(app, collection)` follows a renamed folder. `.atlas-data/` keeps only device-local files: the cache, import backups, unreadable-index copies.
- **Bundles** carry record files by their payload (`comparedBytes`: without `atlasRecord`, and a map's JSON without the collection it names): the export packs that, the import writes payloads, and update fingerprints compare it, so Atlas rewriting a record (after an import under another name, too) is never mistaken for the user changing it. A bundle may not bring `library.json`, `collection.json` or `install.json` (`isLibraryOwnFile`).
- **Content hashes** live in `utils/hashing.ts` (shared helpers, no plugin imports): `sha256` and `hashJson` (SHA-256 of `canonicalJson`) fingerprint bundle files and install records, `hashText` stamps library files and makes derived collection uids and copy ids, `fnv1a32` names thumbnails and seeds dice throws. Their results are stored in vault files or must match between windows, so changing one is a data change; `tests/unit/hashing.test.ts` pins them.
- **Tests**: `tests/unit/library/twoDeviceSync.test.ts` lets two devices edit one library (records, collections created on both, renamed, copied in the file manager, tokens moved) through a sync that loses one side of concurrent edits, and holds that both converge, hold what their files say, and lose no record nobody deleted; `VITE_LIBRARY_SYNC_TRIALS=600` runs more seeds.

- **The folder decides**: an asset belongs to the collection whose folder (`atlas-vtt/collections/<id>/`) holds its file: token art, a map's image, a scene's `.atlasmap`, or the JSON of encounters, player groups, characters and statblocks (`services/vault-sync/assetFiles.ts`). The JSON of scenes and maps only mirrors the index and follows its asset; its place is recorded in `filePath`. Moving an asset to another collection in Atlas moves those files too.
- **Asset manager folders** are vault folders below a collection's tab folder, and the file that places an asset in one is `placingFilePath` (`asset-manager/utils/assetFormatters.ts`): a map's JSON (its image stays in the shared `atlas-vtt/assets/`, so copies share it), otherwise the file the asset stands for. Move to Folder moves only that file (`assetFolderMove.ts`).
- **Vault check**: `AssetService.reconcileWithVault` (`services/vault-sync/`) runs at startup and one second after the vault goes quiet (`plugin/vaultSync.ts`). It recognises collection folders renamed outside Obsidian (reported as delete + create) by finding their files at the same relative paths, relinks records whose file moved by file name, drops records whose file is gone (encounter-like records only when the deletion was seen), and adds records for unknown files. It reads the disk first and then changes the index synchronously, so no other edit interleaves. Renames Obsidian reports are propagated at once, batched per tick (`FileReferenceService.handleFilesMoved`); moves the check finds go through the same path.
- Atlas writes a new file and its record under `assetService.runExclusive`, so the check never adopts the file as a second asset.
- **A collection is named like its folder**: the collection id is its folder name and `name === id` always (`createCollectionRecord`, `moveCollectionRecord`). Renaming in Atlas renames the folder (`renameCollection`), the vault check gives older folders their collection's name once (`planFolderNameFixes`), and imports and forks move the folder to the chosen name; the install record follows (`moveInstallRecord`). Validate names with `collectionNameProblem`.
- **The default collection** is recorded in `AssetMetadata.defaultCollectionId` and read through `defaultCollectionIdOf` / `getDefaultCollectionId()` (older indexes: the collection in `default`). Never hard-code `'default'`; it follows renames, and when its folder is deleted the oldest collection takes over.

## Links to Atlas files in notes
Scenes (`![[Tavern.atlasmap]]`), their snapshots (`#Snapshot name`) and encounters (their JSON, linked with the encounter's name as alias) embed in notes and hover previews as cards (`src/app/links/`).

- **Embeds** go through Obsidian's undocumented `app.embedRegistry` (typed in `obsidianInternals.d.ts`), which serves `![[…]]` in reading view, live preview and link hover previews alike. Atlas claims `atlasmap` and `json`, but the `json` creator returns null for anything that is no encounter (`isEncounterPath`), which gives Obsidian's plain file embed back. An extension another plugin already registered is left alone.
- **Snapshot links**: a link's `#` part reaches `AtlasView.setEphemeralState`; `restoreLinkedSnapshot` waits until the scene is shown loaded and offers the restore with the snapshots panel's confirmation (`snapshots/snapshotRestore.ts`, shared with `useSceneSnapshots`). Names match through `linkSafeName` (the characters a link cannot hold read as spaces), as written first, else ignoring case.
- **`#` suggestions**: `SnapshotLinkSuggest` is moved to the front of `workspace.editorSuggest.suggests`, since the first suggester that triggers wins and Obsidian's own answers every `[[file#` with headings. It triggers only for links that resolve to an `.atlasmap`.
- Encounter files are named by id, so Obsidian's `[[` suggestions cannot find them: links come from Copy link (asset manager, snapshots panel) and the Insert link to scene or encounter command (`atlasLink`, which follows the vault's link format).

## Undo/Redo History
History lives in `src/app/stores/history.ts` and `src/app/stores/history/` (Atlas's own middleware, outermost on the view store; `store.temporal` holds `pastStates`, `futureStates`, `isTracking`, `undo`, `redo`, `clear`, `pause` and `resume`) and tracks only `objects`, `grid`, `background`, `widgetValues` and `exploredEdits`, the count that stands for the explored memory's edits by hand (Dynamic lighting, Editing explored memory). A step (`HistoryStep`) holds the tracked state before and after one GM write or one outermost transaction; recording compares references only, and what a store listener writes during a GM write, `runUntracked` or not, is part of that write's step. Undo and redo put back only what the step changed, entity by entity (a token, a wall, a fog operation, a widget value, the grid, the background): an entity still there is written in its place, one added back takes its old place in its collection, `objects.lightZones` is absent again where it was, and where nothing else changed since, the old objects themselves come back. Everything else stays as it is now, so a write of Atlas itself outside a transaction (`runUntracked`: a renamed file followed, statblock resources filled, a collection's conditions, senses or widgets cleaned up, widgets mirrored from another view) is never taken back by undoing another entity's step. One that changed an entity the step changed too is taken back with it, and since an undo or redo moves its step to the other stack as it found and left the store, the redo or undo after it brings that write back. What a transaction has written while it is open (a drag, a slider or colour picker, or a panel not yet let go), writes of Atlas itself included, belongs to it: an undo or redo then takes it back along with the step, the redo or undo after that brings it back, and a transaction that closes without a step leaves it to be taken back with the steps next to it. The same holds while a GM write's listeners run: a step recorded there, or a transaction closed there, meets the steps next to it as the former implementation's did (`mark` in `history/historyStore.ts`). `forgetExploredEdits` compares the steps with the store as it is now, which may be ahead of them (a transaction under way, an undo being announced), and leaves their sides next to the present as they are. Undo and redo write below immer and persist and are never steps themselves. The attribution and transaction state belongs to each store. `tests/oracles/historyBaseline/` keeps the former implementation, and the `historyParity` tests hold undo and redo to it wherever nothing else changed the scene in between.

- **One gesture = one undo step**: any interaction that writes to the store while the pointer is down (token drag, pin drag, wall vertex/light drag, eraser sweep, live-updating config panels) must call `beginHistoryTransaction(store)` when it starts and `endHistoryTransaction(store)` when it ends, including on cancel/destroy. Multi-step edits use `runHistoryTransaction(store, fn)`; writes that must never be undoable use `runUntracked`. A gesture that is cancelled puts back what it changed and closes its transaction with `abandonHistoryTransaction`, which leaves no step and keeps a transaction around it open (`discardHistoryTransaction` closes all levels).
- **Prefer a single store action** for bulk edits (`updateTokens`, `setTokenPositions`) over raw `store.setState` with an Immer draft.
- Renderers that derive state from `objects` (vision, spatial audio) subscribe to the `objects` reference, so undo/redo refreshes them without dirty flags.

## Widgets
- Every widget of a collection is in its library, `CollectionSettings.widgets`; the widget settings of each scene list all of them (`useCollectionWidgetLibrary`). A widget with `scope: 'collection'` is on in every scene with one shared value, stored on its library entry, and never in scene files: `partialize` strips it via `withoutCollectionWidgets` (`src/app/utils/collectionWidgets.ts`). Other widgets are on only in scenes that hold a copy in their file, each with its own value; their library entry keeps the start value (`pickLibraryWidgets`).
- A scene switches widgets off with `WidgetSettings.offWidgets` (store `setWidgetOn`, read with `isWidgetOn` in `utils/widgetActivation.ts`): its own widgets keep copy and value while off, and a widget on in every scene makes an exception there. `visible: false` is only what older versions wrote to hide a widget; it counts as off and switching the widget on clears it. The panel never sets `visible` any more.
- `WidgetSyncService` applies the library when a map finishes loading (shared widgets in, the scene's copies take the library definition and keep their value), adds the widgets a loaded scene holds but the library lacks (scenes from older versions, scenes moved in outside Atlas; never on a mere `mapPath` change, whose widgets still belong to the old collection), mirrors all widgets between views of the same scene and writes through `CollectionWidgetStore` (debounced). Changes made while `isMapLoading` is true are loads, not edits, and are never propagated.
- A view's edit reaches the library as a diff against what that view was last shown (`withCollectionEdit`), and only adds or changes entries: removing a widget from a scene switches it off there. Deleting is explicit (`deleteCollectionWidget`: open maps, map files, snapshots, then the library), so a scene never brings a deleted widget back. A view whose `mapPath` changes while open (scene moved to another collection) takes the new collection's widgets at once.

## Pin icons
- Pin icons are game-icons.net glyphs (`src/app/types/pinIconPaths.ts`), catalogued with names and heraldic tones in `src/app/types/pinIcons.ts`: the palette row (`PIN_PALETTE`) and the place groups of the location slot's flyout (`PIN_PLACE_GROUPS`). Every path must be offered exactly once (a test enforces it). Place groups run from world scale down to a room; the flyout lays them out eight per row and moves the arrow keys along those rows, so a group may end in a short row.
- Pins store the icon id. Never rename one; older pins store Lucide ids, which `resolvePinIcon` maps through `LEGACY_PIN_ICONS`, so add a mapping instead.
- The canvas rasterises each glyph once in white (`pixi/utils/pinIconTexture.ts`) and tints it with the tone of the active theme.

## Game system presets
- A preset (`SystemPreset`, `src/app/types/systemPresetTypes.ts`) holds a collection's `SystemRules`: `gridDefaults`, `conditions`, and optionally `senses`, `lightPresets`, `defaultTokenVision`, `dice`, `resources` and `widgets`. The collection records the preset it came from in `CollectionSettings.systemPresetId`; "edited" is derived by comparing rules (`sameSystemRules`, condition ids ignored), never stored.
- Built-in presets live in code (`src/app/gameSystems/builtInPresets.ts`) with ids prefixed `builtin:` and condition ids derived from preset and name. Never change those ids: collections and tokens point at them.
- User presets are one JSON file each in `atlas-vtt/system-presets/` (the id inside the file is the identity, never the path) and read only through `SystemPresetService`, which validates every entry (`presetValidation.ts`) and edits stored entries field by field, so data from a newer Atlas survives. Bundles carry a collection's user preset (role `system-preset`, format 8), matched by id like templates.
- Applying a preset (`rulesOfPreset`) copies its measurement and its conditions with the preset's own ids; nothing of the previous system carries over. Senses and light presets are not copied: the collection reads its preset's (`collectionSenses`, `collectionLightPresets`) and stores a list of its own only once the GM edits it, so a corrected built-in sense or light reaches every collection that did not; `sameSystemRules` treats an unset list as the preset's.
- A preset may add collection-wide widgets (`SystemRules.widgets`, e.g. Shadowdark's one-hour torch timer). They are not part of the modal draft or of `sameSystemRules`.
- Every save of a collection's settings runs `syncCollectionSystem` (`services/collectionSystemSync.ts`), which makes the stored state match the settings instead of diffing old and new: the collection gets exactly its preset's widgets (`withSystemWidgets`: other presets' widgets go, missing ones are added, a running timer keeps its value, user widgets stay; written through `WidgetSyncService.forApp(app).editCollectionWidgets` so open scenes update, or straight into the settings when no map is open), and `removeUndefinedConditions` (`services/collectionConditionCleanup.ts`) removes every condition the collection does not define from open map stores (untracked, then saved), closed map files and scene snapshots; `removeUndefinedSenses` (`services/collectionSenseCleanup.ts`) does the same for senses the collection no longer defines, on tokens and in the default vision (a list that loses its last sense is removed, so the token follows its statblock again).
- Deleting a user preset (`services/systemPresetDeletion.ts`) resets every collection that records it to `vanillaSystemSettings()` (default measurement, no conditions, no default widgets, no preset) and syncs it with the preset list from before the deletion, so the deleted preset's widgets are recognised and removed.

- A preset also brings the collection's token resources (`SystemRules.resources`, see Token resources). A map file's `tokenSettings` replaces the store default as a whole, so always write complete settings (`DEFAULT_TOKEN_SETTINGS`). Scene-wide edits go through `updateCollectionScenes` (`services/collectionScenes.ts`).
- **Dice rules** (`SystemRules.dice`, `CollectionSettings.dice`): the default roll (`1d20`, `2d12`) and the crit rule (`natural`, `roll-under`, `doubles`, `high-total`, `none`). Read them only through `collectionDiceRules` (`gameSystems/diceRules.ts`): the collection's own, else its recorded preset's, else `1d20` natural. `DiceTool` gets them from its map's collection (`mapDiceRules`), adds a bare bonus (`+3`) to the default roll and stores the crit on the result (`DiceRollResult.crit`, `tools/diceCrit.ts`, which looks only at the default dice). Everything that shows a roll reads `result.crit`; never re-derive it.
- **Dice input boundary**: `parseFormula` (`tools/parseFormula.ts`) checks the entire expression before any randomness is consumed: at most 64 characters, 10 terms, 100 dice and 1,000 faces, with constants of at most four digits. `rollFormula` takes only its parsed result. `DiceTool` validates both the input and any default-roll completion, returns `null` on rejection and calls its supplied error handler without emitting a roll or recording history. Its random, roll-id and roller-label providers are supplied by `ToolController` through `offlineDiceInputs`; offline behavior keeps `Math.random`, the existing id format and the translated Player label. The tray stays open and keeps its selection after a rejected roll.
- **Initiative rolls**: `createInitiativeActions` receives its state getter and random provider from `storeFactory`. Roll totals and modifiers are computed before the Immer recipe runs; the recipe only applies totals and the existing sort. `rollInitiativeDice` requires its caller’s random provider.
- **Dice events**: `DiceTool` emits `dice-rolled` and `dice-history-cleared` on its view’s `ServiceManager` bus. The view’s cards, sound observer and history hook subscribe there, never on `document`. The history hook owns persisted log updates; its Clear action delegates to the tool. A statblock carries its owning `viewId` for routing only; a closed owner never falls back to another map. The player window receives `diceEvents` with its frame source, keeps that source while holding a frame, and drops its subscriptions and old cards when switching views or releasing the source.
- **Exploding dice** (`DiceRules.explode`, unset is off; `tools/diceExplosion.ts`): which dice roll again (`default` dice as for criticals, or `all`), whether a die rolled for an explosion explodes in turn (`repeats`), how many of the highest faces explode (`highFaces`) and how many of the lowest roll again and subtract (`lowFaces`). No setting names a game: Savage Worlds is all dice, repeating; Cyberpunk RED the default die, once, one low face (built in). A chain has one direction, set by its first die, and goes on only on a high face; every die keeps one face that does not explode; at most `MAX_EXPLOSIONS` extra dice per die. A term's own notation wins over the rule and is Obsidian Dice Roller's (`2d6!` once, `!3`, `!i`; `!!` reads the same); statblock text takes all but the bare `!`, which there ends a sentence. Extra dice are ordinary `RolledDie`s marked `exploded` (a subtracting one `negative`), right after the die they were rolled for; criticals look at the original dice only. Write dice out through `tools/diceLabels.ts` (`6! + 4`, `1! − 7`). Read and edit the rule through `gameSystems/diceRules.ts` (`parseExplodeRule`, `withExplodeScope`). The Dice tab never shows the rule's face counts bare: it says what the rule does to the collection's own die (`gameSystems/explodeRuleText.ts`), offers switches for the two common choices and folds the counts away.
- New collections are created by `CreateCollectionModal` (asset manager) through `createCollectionWithSystem`: no system, a saved preset, or a system set up on the spot and saved as a preset.

## Token resources
- A collection defines up to six expendable resources (`MAX_RESOURCES`; `CollectionSettings.resources`, ordered `ResourceDefinition`s: HP, Cairn's STR, Daggerheart's Stress, ammunition); presets bring theirs (`SystemRules.resources`, compared by `sameSystemRules`, which ignores `visibleToPlayers`: what players see is the table's choice). Read them only through `collectionResources` / `mapResources` (`src/app/resources/collectionResources.ts`; React: `useMapResources`): a map outside every collection keeps the two bars every map had (HP and the secondary bar), and a map whose collection the index does not know yet tracks HP (`TokenRenderer` redraws once the index is loaded). A collection saved before resources existed gets its list stored once at start (`storeLegacyResources`, `legacyResourcesMigration.ts`): its preset's (HP without one), plus the old secondary bar (key `stress`, named "Secondary resource" where the preset has no name for it) when its default widget was on or one of its scenes shows it; until then it reads as its preset's. The check also runs after a bundle import, and a collection that could not be read makes it fail, so the player carry-over waits for the next start. The default widgets `hpBar` / `stressBar` keep the meaning older versions read: whether a new scene shows that bar (`hiddenOnNewScenes`; unset is off, and a collection without default widgets shows HP only). They never decide whether a resource is defined. `rulesOfPreset` and `vanillaSystemSettings` set them from the resources (`barWidgets`), and the settings draft switches one only when its resource came or went (`withChangedBars`). A resource whose direction is `static` is a fixed value (an armour class): it shows its `max` as one number on a full bar or ring, is never spent or defeated, has no controls on the canvas and no row in the DM screen, and is edited in Edit Token.
- A definition names the statblock field (dotted path, `stats.0`) that supplies the maximum, a direction (`drains` starts full, `fills` starts at 0), a colour, `defeatedWhenSpent` and `visibleToPlayers`. Its socket is its `slot` (0–5; a definition without one takes the first free socket in list order, so presets and older lists read as their order; resolve sockets only through `slottedResources`, `resourceSlots.ts`), and the socket decides the shape (`shapeOf`): slots 1–2 are bars below the token, slots 3–6 wheels that show only while the token is hovered or selected, never in the player view: 3–4 on its right, 5–6 on its left, as a mirror. Its `key` is derived from the name when it is first saved (`withFinalKeys`) and never changes: tokens key their values by it, so deleting a definition only hides the values and adding one of the same name finds them again.
- Tokens hold `resources: Record<key, { current, max }>` and `overriddenMax` (keys whose maximum was set by hand and no longer follows the statblock). `current` counts in the resource's direction: remaining when draining, used when filling. HP is a normal resource: only the player initiative bar (`PlayerInitiativePanel`) and the Daggerheart box sync (`statblockVitalsSync`, whose boxes Fantasy Statblocks names `hp-N` / `stress-N`) read the keys `hp` and `stress`; hit dice find the hit point resource by its field (`isHitPointsKey`). All rules live there as pure functions (`resourceValues.ts`: clamp, spent, defeated, kill and reset; `resourceFields.ts`: field lookup and parsing; `statblockResourceValues.ts` / `statblockResourceSync.ts`: starting values, statblock changes, and `fillMissingResources`, which starts a resource defined after a token was placed when its map loads). Change a value with `resourceUpdate` on the token as the store holds it at that moment, never on one captured earlier: it writes the whole `resources` record.
- `visibleResources(token, definitions, viewer)` is the only place that decides what a viewer sees, in definition order. The canvas draws bars in `ResourceStack` under the token's bottom-edge anchor and wheels in `ResourceWheels` (`pixi/token-renderer/resources/`) under two more anchors on the token's bottom edge, one past each resize button (`wheelAnchor` and its mirror; `ResourceSlot.kind` `wheel` / `wheel-left`); all are updated in place. A wheel has the bars' look (`BAR_LOOK`: border, dark track, flat fill; `RESOURCE_NUMBER_STYLE`), is one closed ring when full, divides a whole maximum of 2 to 8 with thin ticks (`wheelGauge`), and is drawn `DRAW_SCALE` times larger and scaled down: PIXI builds a curve from a number of straight pieces that follows its local radius, so a small circle scaled up on screen shows corners. The wheel stack stands on the nameplate's top line and grows upward with the UI scale, as the bars grow downward, so at no size (a selected token's UI is larger than its resting size below zoom 2.25) can wheels meet the nameplate, the bars or their buttons. Slots are in anchor units and never depend on the scale. `TokenControlsUI` has the same anchors and builds its click areas and +/- buttons from `TokenUIRenderer.getResourceSlots` (`kind` names the anchor); a wheel gets a stepper on its outer side, away from the token. The selection frame encloses the token and its bars (`getBarsReach`), never the wheels. Test token UI at a zoom below 2.25 (`zoomProvider`), where the selected size differs from the resting one. Edit Token reads the same list; initiative cards show the resources that defeat a token (HP); initiative entries hold no values of their own. A resource that defeats its token warns as it runs low (`resourceColor`: its own colour, yellow below 70%, red below 30%), on the map and in the tracker.
- **The Resources tab** (`collection-settings/ResourcesTab.tsx`, `resources/`) edits them on a picture of a token: six sockets in the map's places (`SOCKETS`), any of which may be filled; a click selects a socket, a fan of round buttons (`ResourceFan`, framer-motion, tooltips on the fan's outer side) sets direction, defeat, player visibility and remove, and the card under the token (`ResourceCard`) holds name, statblock field (with the collection's statblock fields as chips) and colour: one of the twenty in `RESOURCE_COLORS` (`resourceColors.ts`), never a free colour picker, and never the warning yellow and red. The placeholder under the card must not take pointer events (it once covered the card's inputs). Dragging onto another socket moves or swaps (`movedResources`). A resource placed and left untouched is dropped when its socket closes; Escape closes the socket and stops there, since the dialog listens for Escape on the document. The dialog's content area (`SettingsContent`) keeps its scrollbar inside its padding (`atlas-scroll-padding`, `useScrollbarGutter`), so a tab that starts to scroll does not move; the browser tests run with scrollbars shown (`vitest.config.mts` takes Playwright's `--hide-scrollbars` off): a hidden scrollbar takes no room, so the shift could not be measured.
- **A map decides which resources it shows**: `tokenSettings.hiddenResources` lists the keys the GM's canvas hides (`sceneVisibility.ts`; the scene's token settings have one switch per resource). The player window never reads it: it follows each resource's `visibleToPlayers`, which the player view settings switch per bar of the open scene's collection. New scenes get their token settings from `newSceneTokenSettings`, and a scene that joins a collection takes the two bars a new scene there shows (`showNewSceneBarsInJson`; left alone when the collection has no default widgets).
- **The DM screen** lists `tokenQuantities` (`statblockQuantities.ts`): the collection's resources, then every further quantity the statblock names (mana, luck, a `resources` map, Fate stress tracks), whose numbers live in the token's `resources` under the statblock's key (`mana`, `resources.Momentum`, `stress.0`). Boxes only where the statblock draws tracks (Daggerheart layouts, Fate stress); gauges elsewhere.
- **Files keep the format every Atlas reads** (`resourceFileFormat.ts`): on disk a token has `hp`, `stress` + `maxStress`, `hope`, `statblockResources` (every other key) and the two override flags, a scene's token settings the switches `showHPBars` / `showStressBars`, and initiative entries copies of `hp`, `stress` and `isDefeated`. `tokenFromFile` / `sceneFromFile` read them, `tokenToFile` / `sceneToFile` write them, and they undo each other. Scenes are converted when their file is read (`createAtlasStorage().getItem`) and when it is written (`SceneFileWriter`'s serializer, once per write), encounter states at save and spawn, closed maps in `TokenStatblockLinkService`. Nothing else may know these fields, and anything new that writes token state to disk goes through `tokenToFile`. `ATLAS_VERSION` stays 4: an older Atlas loads a map with a higher version empty and saves that over the file, so never bump it for a change old versions can ignore.
- **Linking a statblock** starts the resources the statblock supplies and keeps what the token held of the others (hand-set hit points, the DM screen's quantities), on open and closed maps alike; unlinking clears them all. **Bundles** compare settings through `comparableSettings` (`collectionBundle/bundleSettings.ts`): resources that only restate what the settings read as before they were stored are no edit, so updates of untouched collections stay silent; settings taken from a bundle that names no resources keep the vault's (`settingsFromBundle`).

## Valued conditions
- A condition may carry a number on each token (`ConditionDefinition.valued`, e.g. Pathfinder's Frightened 2, D&D's Exhaustion levels). Tokens keep the numbers in `conditionValues` beside the `conditions` list; a valued condition without an entry is 1. Read and change them only through `src/app/utils/conditionValues.ts` (`conditionValue`, `setConditionValue`, `removeCondition`) or the store's `changeTokensConditionValue`, so an emptied list or map is deleted rather than left behind.
- The canvas badge shows the number in a pip (`ConditionBadge.ts`), the hover card and labels read "Frightened 2" (`conditionLabel`), and the Conditions menu gets a stepper (`ContextMenuEntry.stepper`, also driven by the + and - keys). The condition cleanup removes stale numbers with their conditions.

## Moving and copying assets between collections
- Always go through `transferAssets` (`src/app/services/assetTransfer/`); `updateAsset` cannot change `collection`. A move keeps asset ids (encounter refs and install records depend on them); a copy gets new ids, and copies made together are rewritten to point at each other.
- `planTransfer` decides per file from `CollectionReferenceCollector`'s list. Owned files go with the asset: record file, scene map with thumbnail and snapshots, a token's image and thumbnail. A copy duplicates them: `deleteAsset` trashes a token's image, and deleting a token removes every map placement that uses its image path, so two tokens must never share one. Referenced files are shared when they lie outside the source collection folder or belong to a token that stays. Otherwise they go to the target folder under the same relative path: moved, or copied if an asset that stays still uses them.
- A statblock note links to one token, found by the artwork in its `image` field. A token whose artwork was copied keeps its `statblockPath` only when its note was copied along (and relinked to the copy); otherwise the link stays with the original and the result reports it in `unlinkedStatblocks`.
- Moves use `fileManager.renameFile`, so `FileReferenceService` and the open view follow as with any rename. Scene snapshots live in `collections/<c>/snapshots/<scene id>/`: a move takes them along under the same id, a copy writes them under the copy's new id, and renaming a scene file moves nothing; an open moved scene is rewritten through `reloadActiveScene`. A map that belongs to no scene (an `.atlasmap` outside every collection) keeps its snapshots where every map did before, in the hidden folder beside it, on this device only (`snapshotFolderForMap`, `snapshotStorageFor` reads it through the adapter), and that folder follows the map when it is renamed (`followLegacySnapshots`). Loot history is per device, `collections/<c>/loot-history/<device id>.json`, merged on read; a removal or a clear names the rolls it takes away, never a time, so devices' clocks decide nothing. `snapshots/` and `loot-history/` are Atlas' own folders, never assets (`isReservedCollectionPath`). `TransferFiles` journals every step, record files included (`pendingRecordFile`), and undoes them if the commit fails. `commitAssetTransfer` only saves records and tags, in one write. The vault check (`reconcileWithVault`) takes the same index lock, so it never sees a half-done transfer.
- A scene joining a collection is conformed like a new one (`sceneAdoption`): its tokens lose conditions the collection does not define, the map and its snapshots lose widgets the collection's library lacks (the old collection's; `dropWidgetsFromJson`), and the map shows the resource bars a new scene of the collection shows.
- **Scene links never cross collections** (`services/sceneLinks.ts`): a pin may open a note anywhere but only a scene of its own collection (`mayLinkFromScene`), because opening another collection's scene silently switches widgets and rules. The pin search and paste enforce it. Before a transfer the asset manager offers the linked scenes along (`linkedScenesFor`: what copies link to; on a move also what links to the moved scenes); the transfer itself drops every link that would cross (`sceneAdoption` after path remapping; `unlinkStayingScenes` on a move, before the maps move, since `FileReferenceService` would otherwise follow the rename). Older cross-collection links open the scene at the same place in the pin's own collection (`sceneLinkTarget`).

## Creature filters
- The asset manager's Characters tab filters tokens by their linked statblocks (`src/app/creatures/`). Only tokens are listed; a statblock without a token never is.
- Filters come from the statblocks, not the game system: `CATALOG_CREATURE_FILTERS` (`creatureFieldCatalog.ts`) names the fields Fantasy Statblocks layouts share (Challenge rating `cr`, Level, Tier, Type, Traits, Rarity, Alignment, Source), and the sidebar shows each only where the statblocks in view have its field. A collection may switch catalog filters off (`CollectionSettings.hiddenCreatureFilters`, by id) and add filters on other fields (`customCreatureFilters`); read both with `collectionCreatureFilters`. Never change a catalog id. A range filter reads exactly one field so scales never mix; an options filter may merge several (Pathfinder's `trait_01`…).
- `CreatureIndex` (one per app, released in `onunload`) resolves note paths through `resolveLinkedCreature`: the bestiary entry, else the note's frontmatter (Fantasy Statblocks parses notes only with "auto parse" on), else its statblock fence. It re-reads a note on metadata change and all notes once the bestiary settles after an update, and keeps old entries readable meanwhile. React reads it with `useCreatureIndex` (`useSyncExternalStore`).
- `creatureValues.ts` normalises values for every system: ratings (`"1/4"`, `½`, `"Creature 3"`, `"3+1*"`, `−1`) and options (links, Fantasy Statblocks' encoded links and page references stripped, compared case-insensitively). `creatureFilterEngine.ts` is pure: options within a filter are OR (or all required, `match: 'all'`), filters AND, each facet counts as if its own filter were off, and a token lacking a required option's data is hidden and counted in `hidden`. Option filters and the layout facet hold `OptionPicks` (`include` / `exclude`); an excluded value hides every token that has it and keeps those without the field. Edit picks only through `creatureSelection.ts` (`toggleOption` for a click, `toggleExcludedOption` for a double or Alt-click, `withOptionState`). The alignment filter reads parts, not phrases (`alignmentParts`: Lawful, Neutral, Chaotic, Good, Evil, Unaligned, Any; `CE` and `L` abbreviations too) and requires every picked part.
- The filters live in the search, as in Valkenhall's deck builder: typed `keyword:value` tokens (`type:beast`, `cr>=5`, `cr:1/4-3`, `tag:forest`, `statblock:no`, quotes for spaces; `-type:beast` or `type!=beast` exclude where the keyword is `negatable`) with autocomplete for keywords and for the values in view, the filter panel behind the button at the end of the field (`AdvancedFilterPanel`; the button is on every tab and disabled where a tab has no panel yet, so the header never shifts between tabs), and a chip per active filter above the content (`ActiveFilterBar`). The syntax is generic (`src/app/search/querySyntax.ts`); the asset manager's keywords, suggestions and token application live in `asset-manager/search/`. The filters' options and counts come from the open folder and every folder below it (`useCreatureFilters`), what an active filter searches, so a root holding only folders still offers its subfolders' statblocks. Committed tokens leave the text and become filters; the name search uses only the plain words (`useSearchKeywords`), so a half-typed token never empties the list. Tab and Escape in the field stop propagating while the suggestions use them, since the asset manager's shortcuts listen on the document. Cmd+F (Ctrl+F off macOS) is an Obsidian key scope pushed while the search is mounted (`useSearchShortcut`): Obsidian binds Mod+F to "Search current file" and consumes it before any DOM listener. Option values drop private-use characters (rulebook-font glyphs), and the Type filter reads categories without a bracketed detail (`parseCategories`: "Horde (10/HP)" is Horde).
- The Rating sort orders characters by the first of `RATING_FILTERS` their statblock has, grouped by scale, with unrated characters last in either order.

## Translations
- UI text goes through `t(key, values)` (`src/app/i18n/`). English (`locales/en/`) is the source and holds every key; another language is a folder `locales/<code>/` with the same files (typed `Translation`), registered in `TRANSLATIONS` under Obsidian's language code. A missing key falls back to English, and a test checks that translations keep the English placeholders.
- A key's first segment names its file: `palette.moveTool` lives in `locales/<lang>/palette.ts`, spread into that language's `index.ts`. The segment must be a valid identifier and no reserved word (`exportDialog`, not `export`).
- `{name}` placeholders take values; a message with plural forms (`{ one, few, many, other }`, categories of `Intl.PluralRules`) is picked by `count`. Never build a sentence by concatenating translated pieces; join lists with `formatList`.
- The language is Obsidian's (`getLanguage()`), read when the module loads, so texts built at module level are translated too; Obsidian restarts on a language change, so nothing re-renders. `Intl` formatters that should match the texts use `getLocale()`.
- Keys, ids and stored data are never translated: only what is shown. Game system presets, the GitHub issue report and log messages stay English.

## 3D dice
- Rolls show at the top right of the map (top centre in the player window) through `DiceRollDisplay` (`react/components/dice/`): as 3D dice unless the global `diceDisplay` setting is `card` (`dice3d/diceDisplay.ts`; `fast` runs the dice's clock at double speed in `DiceStage`, the linger stays) and `diceSceneToShow` (`dice3d/rollPresentation.ts`) finds real bodies for every die, otherwise as the result card (`DiceToast`). The same component runs in the player window, muted, with `prepare` hiding hidden tokens.
- `src/app/dice3d/` is ported from Fabian's dolmenwood app and must keep its behaviour: pure maths (`dieGeometry`, `dieTour`, `dieMotion`: a closed-form billiard path unfolded at the walls and a pose written down backwards from the target face, not a physics engine), `three` rendering (`DiceRenderer` and helpers) and sample-based Web Audio (`audio/`). The dice land on Atlas' own rolled values (`sceneFromRolls`); nothing re-rolls.
- Rolls show above every overlay of the map, the DM screen included (`$z-atlas-dice-rolls`), since a roll made from a statblock there must be seen; menus still open over them. They hang from `.atlas-top-bar-row`, which therefore must stay no stacking context (absolute, no `z-index`; a fixed element always is one): its bars carry the `z-index` instead. `tests/gpu/diceRollLayer.gpu.test.ts` checks it against the real stylesheet. The asset manager lives outside the map view and stays on top of all of it.
- **Dice land lying on a face** (`restingQuaternion`), turned by a seeded yaw of at most `REST_YAW`, never tilted towards an edge or corner; this deliberately departs from the dolmenwood original, which tilted them. The rolled face lies on top, except on the d4, which lies on it and is read at its tip: `faceMarks` writes three numbers on each of its faces, one per corner. The centre comes down from the tumbling height to `lyingHeight` as the bounce dies (`floorAt` in `dieMotion.ts`), so the body touches the table and its shadow.
- **An explosion is thrown as a chain** (`throwChain.ts`): every die is planned at once (`DiePlan.follows`), but a die rolled for an explosion is not on the table until the die before it has landed (`StageDie.waits`). That die lands with its own burst (`StageDie.burst`: the success sparks upwards, the failure sparks downwards, plus `burst()` in the sounds), then the next is thrown and the wheel starts again. A subtracting die is shown only as part of such a chain. The panel's ripcord waits one throw longer per die of the longest chain (`chainDepth`).
- **What a dice frame may cost**: the dice run at up to 120 frames a second beside a lit map and the player window, each with its own stage. The soft shadow's blur is a fixed cost per frame, whatever the dice: its map is 1024 texels with 12 taps (`SHADOW_MAP`, `SHADOW_TAPS`; 2048 with 24 was nine tenths of a frame's GPU time), and the mirror world is baked at 64 px. So the shadow map is drawn only in a frame that moved a body and the one after (`StageShadow`, `dice3d/stageShadow.ts`; `shadowMap.autoUpdate` is off, and anything else that changes what casts must call `bodiesChanged`), and the stage's clock stops once the light has swelled and no spark burns (`DiceRenderer.isStill`), not after a fixed afterglow. Do not cut the blur to the part of the map the dice cover: VSM draws the floor into the map too, so no texel is empty, and it saved nothing measurable. Ghost materials wait between throws (`GhostTrail.spare`): disposing the last one deletes its shader program, which the next throw then compiled on its first frame. Stages are built ahead while nothing rolls (`warmStages`: four per document, the three standing rolls and one fading out, one per quiet moment, never while dice are on a stage), with a canvas of the panel's size. A panel never asks for another: `DiceRenderer.setView` draws in the bottom left corner of a canvas that only grows, and so does the context's drawing buffer, and the stage clips it, so a roll arriving and one shrinking to a row make no drawing buffers (each took 2 to 4 ms at the moment the morph starts). `setSize` sizes the canvas exactly, for what reads it back (the settings' previews). Before changing any of this, measure: a GPU timer per frame, and `gl.finish()` around the first frame of a throw on a warm stage.
- **One WebGL context per document draws every stage** (`DiceGpu`, made with the document's first stage in `stagePool.ts`). A stage is a scene, a camera, its shadow map and its own 2D canvas: it draws into the bottom left corner of the context's canvas and copies that corner onto its canvas in the same task (`DiceGpu.draw`), pixel for pixel (`tests/gpu/diceSharedContext.gpu.test.ts`), so the panel keeps its element, clipping and stacking. A context per stage held the face atlases, mirror world and shaders once per stage, about 100 MB each with four warmed. Stages share the renderer's shadow map switch, so a stage sets `shadowMap.needsUpdate` right before its own render (`StageShadow.update`). The context is given back only when its window closes or Atlas unloads (`registerDiceStageRelease`), never per throw: a dropped context keeps counting against the browser limit until garbage collection, and one nobody gives back outlives the plugin (a reload once left 400 MB behind).
- The stack state is per display (`rollStackState.ts`): at most three standing rolls; a panel fades (`leaving`) and is removed by its own timer, never by an animation callback.
- A roll that makes room shrinks to a row by animating its real height (`useElementHeight`: the sheet's clip follows its content), never with framer-motion's `layout` size morph: that is a scale, which stretches the corners, border and shadow (all theme variables, so framer cannot correct them) and the dice. Panels use `layout="position"` only. `tests/gpu/diceRollMorph.gpu.test.ts` measures it in a real browser (`npm run test:gpu`).
- **Dice look** (global settings `diceColour`, `diceFont`, read with `getDiceLook`): `registerDiceLookSync` applies it through `applyDiceLook` (`dice3d/diceLookRuntime.ts`) at start, on setting changes and on `css-change` (accent dice take `--interactive-accent`). `dieSkin.ts` holds the active resolved look and paints card and rim; `dieNumerals.ts` holds a 22-cell sheet per font (the pencil drawing, or Oxanium set at runtime) and colours numerals through a scratch cell. The relief always takes the numeral dark. Previews (`renderDicePreviews`) swap the look and restore it within one task. CSS numbers follow `.atlas-dice-font--scifi` via `--atlas-dice-font`.
- Rolls shown in 3D make their own sounds; `DiceToastObserver` plays the old reveal sound only for result cards.

## Token stacking
- The token put on a square last lies on top. The order is `token.layer` (unset is 0), which the token's group takes as its `zIndex` in the sorted token layer (`SpriteFactory`, `TokenRenderer.syncTokens`); `hitTestTokens` picks the topmost token under the pointer by the same order. Tokens of one layer lie in the order their sprites loaded.
- Only `raiseTokens` (`src/app/stores/tokenStacking.ts`) writes it: above every other token, keeping the order a group has among itself, and nothing when the tokens already lie on top. Every action that puts tokens on the map calls it in its own store write (`addTokens`, `insertMapObjects` for paste, duplicate and Alt-drag copies), so anything new that adds tokens must too.
- A drag ends in `dropTokens`: the places, the raise and letting go of the held tokens in one write, inside the drag's history transaction. Sight therefore works a drop out once (a `layer` written while the tokens are still held would build the scene twice), and undo puts place and order back together. Moves that are not drops (`moveToken`, `setTokenPositions`: re-snapping, animations) never change the order.

## Panning
- **A right-drag pans in every tool.** The viewport's `drag` plugin runs on the right mouse button (`PixiAppManager`) and is never paused for a tool, only for the length of a gesture (token, pin, text and drawing drags). Never set `viewport.pause` for a tool: it stops the zoom too.
- Tools start their gestures on the primary button only (`e.button === 0` on `pointerdown` and `pointertap`; PIXI sends `pointertap` for the right button too, so a pan ends in one). Never check the button on `pointerup`: a browser sends it only when the last button is released, with that button, so a stroke whose release is ignored stays open.
- A right-click menu that opens away from a small target (fog, linked hexes, the wall tool's selection menu) opens when the button is released in place, through `watchClick` (`pixi/utils/clickRelease.ts`), and its press stays unhandled. The menus of tokens, pins, drawings and text open on the press.

## Initiative
- **The GM chooses the combatants.** A token is in the tracker only once it was added (token menu, Add to Initiative, for the whole selection; the clicked token decides between add and remove). Nothing adds tokens by itself; the tracker only drops the entry of a deleted token. This is what Foundry, Roll20, Fantasy Grounds and Owlbear Rodeo do.
- **One rule decides what the players see**: `PlayerInitiativePanel` lists every entry whose token is not hidden (`token.isHidden`), so the players' list is the GM's without the hidden ones. Never filter it by line of sight or light: the list then changes as tokens move and the GM cannot tell what it shows (tried in 0.5.0-beta.2, taken out again). A creature the players must not know of is hidden, on the map and in the list alike.
- The GM's card of a hidden token is translucent and carries a crossed-out eye (`InitiativeCard`), and the card's menu hides or shows the token (`updateTokens`, an undo step like on the map). While such an entry has the turn, the players' list marks none.
- Both lists draw a token as the map does, from the token's own `showRing` and `ringColor`: the GM's card with `TokenPortrait`, the players' panel, which is built with the DOM, with its twin `createTokenPortrait` (`shared/tokenPortraitElement.ts`: the same elements and classes, so `token-portrait.scss` styles both). Never a bare `<img>`.
- **A collection decides how its tracker runs a fight** (`InitiativeRules`, `types/initiativeRulesTypes.ts`): `turn-order` (a number each, rolled with `roll`, highest first) or `sides` (players and opponents act as two blocks, `firstSide` first, nothing rolled: Cairn). Read the rules only through `collectionInitiativeRules` (`gameSystems/initiativeRules.ts`): the collection's own, else its recorded preset's (`SystemRules.initiative`), else a d20 in turn order; on a map `mapInitiativeRules` / `useMapInitiativeRules`. Like senses, a collection stores rules of its own only once the GM edits them (the settings' Default Widgets tab, `InitiativeFields`): applying a preset clears them, an edit that ends at the system's rules again stores nothing, and `sameSystemRules` reads unset as the preset's.
- **A fight keeps the mode it was started in.** `startCombat(rules)` writes `initiative.sides = { first, active }` for a fight by sides and removes it otherwise; `nextTurn` / `previousTurn` go by that field alone (`initiative/turns.ts`), so the hotkeys in `UIRoot` need no rules and a change of the settings reaches the next fight. Both lists show groups while `initiative.sides` is set, or, without a fight, while the rules say `sides` (`listedBySides`). By sides the lists ignore an entry's `isActive` (the store still sets it on the first entry added); the side with the turn is marked. A new round clears every `sitsOut` (an entry that does not act this round: Cairn's failed DEX save in round 1).
- **A token's side is the token's** (`BaseToken.side`, read with `sideOf` in `initiative/sides.ts`): unset, a token with vision switched on is the players' (the lighting takes those for the party) and any other an opponent. It is not on the entry, so it survives clearing the tracker; the card's menu moves a token to the other side (`updateTokens`, an undo step).
- **The turn stays in view**: when the turn moves, both lists scroll to the active card (`nearest`) or the top of the active side with `scrollWithin` (`utils/scrollWithin.ts`), which scrolls the list alone; `scrollIntoView` would scroll every ancestor that can scroll. The players' panel is drawn anew on every change, so it scrolls after every draw. `useMapInitiativeRules` and `useMapResources` read their collection again when its settings are saved and once the asset index has loaded (`useCollectionRulesRevision`): a view built before that reads its map as outside every collection.
- `resetInitiative` (the tracker's Clear button) removes every entry and ends the fight. `rollAllInitiative(roll)` / `rollEntryInitiative(id, roll)` roll the collection's dice; the tracker passes `rules.roll`.

## Rendering and teardown
- **Fog coverage**: `fog/fogCoverage.ts` replays saved paint and erase operations into bounded eighth-pixel shapes. `lighting/polygonClip.ts` owns the only clipping-library import. `FogOfWarRenderer` owns one map-aware `FogCoverageCache`, shared with `FogCanvasCompositor` and visibility consumers through `getCommittedCoverage()`. Immutable record identity avoids repeated geometry work; a single appended operation can reuse the previous shape, while observed undo/redo snapshots replay. Every lookup checks map identity, so an earlier subscriber can safely read the new map before the renderer clears its old pixels. The compositor draws committed rings with NonZero winding and keeps temporary strokes separate. Invalid committed geometry produces an opaque picture and excludes player tokens and door badges until valid data arrives. Per-operation sprites remain invisible editing helpers.
- **Fog and visible tokens**: `PlayerSightTokens` composes committed fog with lighting for player captures, session view and existing peek. Fog tests the displayed sprite centre (the stored position before a sprite exists), including on unlit scenes and when the lighting controller is absent. Covered tokens lose their art, labels, bars, conditions, sensed outlines and drag rulers. Fog also hides held tokens without ending their captured drag; the held exception applies only to lighting. Membership is cached by displayed object, coverage identity and both coordinates; movement updates only that token's outline. Door badges and their player hit targets require current sight and an uncovered midpoint; unlit scenes still show no player door badges. Fog presentation never changes sight sources, explored memory or the normal GM view.
- **Render on change**: `src/app/pixi/RenderScheduler.ts` replaces the Application's per-tick render. It renders only when PIXI's render groups hold pending changes (moved, added, removed or hidden children; updated Graphics, Sprites or Text). Ticker callbacks still run every frame. Anything PIXI cannot see must call `requestRender(app)`: pixels uploaded into an existing texture (`source.update()`), hand-animated filter properties, renderer settings, off-screen renders that consume pending updates (`generateTexture`).
- **Destroy with `destroyTree`** (`src/app/pixi/utils/destroyTree.ts`): in PIXI 8 `destroy({ children: true })` keeps every Graphics' geometry registered with the renderer until the app is destroyed. Never detach a display object with `removeChild` alone when it is not reused.
- **Rebuild only what changed**: store-driven renderers compare the new record with the previous one (Immer keeps unchanged references) and move objects in place instead of recreating them on every update, e.g. during drags.
- **Token UI sizing** (`src/app/pixi/token-renderer/tokenSizing.ts`): all token UI lives in world space in anchor containers on the token's edge, laid out in UI units (1 = a medium token on a 70px grid). Resize and rotate handles scale with the token via `tokenUIScale(spriteSize)`, like Owlbear Rodeo, and don't turn with it (resize left/right, rotate at the top). Resource bars, nameplates and condition markers (`TokenUIRenderer`) do not follow the token's size: they rest at `restingTokenUIScale(gridSize)` while unselected or dragged, and a selected token's grow to `selectedTokenUIScale`, a constant screen size like map pins (recomputed on viewport zoom). The +/- controls take the bars' scale through `UIManager`. `InteractionController` reports held tokens, so a press that selects a token and a drag keep its bars at rest until release. Canvas animations use `ValueTransition` (`src/app/pixi/utils/ValueTransition.ts`) with the motion tokens from `src/app/utils/motion.ts`.
- **Player window**: `PlayerFrameMirror` (`services/`) captures in `RenderScheduler`'s before-render hook (`setBeforeRender`): player layers and camera on, render, copy, layers and camera back (`captureBeforeRender`), and the DM's own render that follows in the same task restores the canvas, so a mirrored frame costs one extra render and the DM never sees it. It mirrors at most `PLAYER_MIRROR_FPS` (60) frames a second on any display (slots follow each other, so the remainder of a 75 or 144 Hz frame carries over) and none while the player window is hidden; a skipped frame or a player-visible change without a DM render (`markStale`: settings, freeze, a released hold) makes its loop call `requestRender` once a frame is due, so players never stay on an older state and an idle map is not rendered. Whatever a capture changes must be restored before the DM's render, or the stage keeps rendering. While the source's store has `isMapLoading`, the mirror captures nothing live: a load rewrites the store in steps and the canvas shows the scene half built (unlit, without fog or line of sight), which would give the map away. Players keep the last frame, the mirror stays stale, and the first display frame after the load asks for the finished scene; sources without a store are captured as before. A hidden DM window (no ticker) and canvases without a scheduler are captured directly, with a render to restore. Popouts are closed when the main window unloads, since Obsidian leaves them open across reloads and each one would keep the previous session alive.

## Experimental features
Features that ship for the GM to try are off until switched on in the command palette's Experimental features page (`command-palette/ExperimentalFeaturesPanel.tsx`: one switch per entry of `EXPERIMENTAL_FEATURES`, `src/app/experimental/experimentalFeatures.ts`). The choice is global, stored in Atlas' settings under the feature's id (`AtlasSettings.experimental`; never rename an id) and read only through `SettingsService.isExperimentalOn`: `experimentalFeatureOn(app, id)` / `dynamicLightingOn(app)` outside React, `useExperimentalFeature(id)` in React, which follows the switch at once. A vault whose settings cannot be reached reads as off. Tests switch a feature on with `withDynamicLighting(app)` (`tests/mocks/experimentalFeatures.ts`). `featureFlags.ts` stays for what a build must not offer at all.

- **Dynamic lighting** (`dynamicLighting`) is the first. Off means the view has no lighting at all: `LightingFeature` (`pixi/lighting/LightingFeature.ts`) owns a view's `LightingController` and builds it only while the feature is on, on an open map too (from the scene as the store holds it), and takes it off an open map when the GM switches it off (`LightingController.remove`: what is being edited ends and pending memory is saved as before an unload, `TokenRenderer.clearLighting` gives the pointer and the tokens' visibility back). The map then shows unlit and players see everything; the scene keeps its walls, lights, `lighting` and explored mask, so switching back on restores it. Without a controller the lighting tool falls back to the move tool, whoever set it.
- What is hidden while it is off: the toolbar's Lighting tool, the `wall` and `lightingPeek` shortcuts (`experimental` in `MAP_HOTKEYS`; `availableHotkeys(player, isOn)` leaves them out of matching, the help and the settings list, while their keys stay reserved), the light and zone popovers and the scene lighting panel (`UIRoot`), Vision and Carry light in the token menu, the vision and light fields of Edit Token, the collection settings' Vision tab and the conditions' "Effect on sight". Anything new that belongs to lighting must ask the same question.

## Dynamic lighting
Walls, lights and line of sight (`src/app/vision/`, `src/app/lighting/`, `src/app/pixi/lighting/`), owned per view by `LightingController`.

- **Model**: sight × light × senses. `SceneLighting` (`enabled`, `ambient` 0–1) is per scene and never undo-tracked. Tokens see with `vision` (`range` blank = unlimited, `angle`, `senses`) and may carry a `light`; placed lights are `objects.lights`. Every distance in this data is **game units**; convert only with `gameUnitsToWorld` (`lighting/lightingUnits.ts`).
- **Light levels** (`vision/lightLevels.ts`): every point is `bright`, `dim`, `dark` or `magical-dark` (inside a darkness source, below). `lightLevelAt` is the one function the rules read: the brighter of the ambient light (`ambientLevel`: dark below `litThreshold`, bright from `brightThreshold`, dim between) and the lights that reach the point (`LightReach`: bright within the bright radius, dim within the dim one, where no wall is between).
- **Magical darkness** (`LightEmission.darkness`, radius `dim`; `priority?`, unset 0): a light that swallows light instead of giving any, ending at walls (it is no occluder: a viewer outside sees past it, and light beyond it is untouched). *Rule*: inside it `lightLevelAt` ignores the ambient light (the scene's and a zone's) and every light whose priority is not higher than the darkness' (ties go to the darkness; any higher priority, by whatever fraction, outshines it); a light that outranks it lights the point at its own level, otherwise the point is `magical-dark`, which a sense perceives by `sees.magicalDark` (truesight, devil's sight, greater darkvision see; 5e darkvision does not; PF2e darkvision as dim, at every rank). Two more rules, both in `vision/magicalDarkness.ts` and applied by `SceneModelBuilder` (and the Canvas fallback) before picture and rule are built: a light whose flame stands in a darkness it does not outrank is put out, inside and beyond (`quenched`: it is in neither the engine's lights nor the reaches), and a vision token standing where the level is `magical-dark` loses its sight and every sense of the eyes unless that sense sees in magical darkness (`sourcesInDarkness`: like Blinded, senses that work while blinded stay); it is still shown within its footprint. *Picture*: a darkness is drawn as the polygon the rule counts (`EngineLight.area`: `SceneModelBuilder` hands the reach's own polygon on, so it is traced once; an engine given a darkness without one works it out the same way, `LightingWorld.darknessOf`), as a fan (`darknessShader.ts`), not from a traced tile: walls are lines without thickness there, so a wall inside a darkness casts no shadow of its own into it and rule and picture cannot differ. The light map draws lights and darknesses in order of priority (`byPriority`): a darkness erases what was drawn before it (blend `erase`: 1 inside, fading to 0 over the last `DARKNESS.rim` world px before the radius, never beyond it; the rule counts the rim as dark, so it is narrow). `DarknessMap` (`rgba8unorm`, world space, created with the map's first darkness source and freed by `LightingWorld.trim` once the last is gone and the composite has let go of it) holds that coverage in red, by which the composite takes out the ambient light, the bounce and what is perceived without light, in green what a sense that sees in magical darkness perceives (`pierceShapes`: its area at 0.5 as dim, 1 as bright; footprints too, so a party token standing in darkness still shows), and in blue where a light near the darkness would shine (its `area`: the lights a darkness swallows are not in the light map, so nothing else tells). The polygon ends on the walls' centre lines, so past a wall only the wall's own core (1.5 texels) can take of the darkness: the leak fuzz holds darkness to that, and the picture to the rule a texel inside the area's outline. Where the darkness takes something from the players' picture (ambient light, a light's light where the rule counts it, what a sense that does not see in it would show) they see a faint cool veil in its place (`DARKNESS.veil`, `taken` in the composite), which tells magical darkness from the unlit dark; over unlit floor and over explored memory there is none, since a veil there gave away where a darkness is although it swallows nothing: an unlit room looks the same with the source as without. The GM sees the dim map under a stronger veil in all of it. The composite reads the map only while `uHasDarkness` is set, so a scene without darkness is pixel-identical and costs nothing. Explored memory leaves darkness areas out unless such a sense sees them (`ExploredShapes.except`). The Canvas fallback paints them black, cut open where a sense that sees in magical darkness looks, and reports them as its only reaches. In the popover a darkness has its kind (own crescent glyph) and one radius; a light has a switch "Outshines magical darkness" (priority 1).
- **Lights that follow the ambient light** (`LightSource.activeBelowAmbient`, 0–1, placed lights only; unset, or 1, always shines): a street lamp shines only while the scene's ambient light is at or below its level, so one set to dusk burns at dusk. Read it only through `lighting/lightActivity.ts` (`ambientGate`, `isLightOn`, `sleeps`). `activeLights(lights, tokens, ambient)` leaves a sleeping light out, and the picture (engine lights) and the rule (`LightReaches`) are both built from that one list, so a lamp lights neither or both. `SceneModelBuilder` builds anew when an ambient change wakes a light or puts one out (`awakeLightsChanged`), not on other ambient changes. The marker carries a small moon and is dimmed while the light sleeps (`LightMarkerLook.moon`; `lightMarkerLook` takes the ambient light); the popover's Shines row offers Always, From dusk and At night (`LIGHT_SCHEDULES`, levels from `lighting/timesOfDay.ts`, which the lighting menu's time of day reads too). "Always" removes the field: `updateLight` takes `LightChanges`, where a field given as undefined is removed, so a light can be put back exactly as it was (a cancelled first turn leaves no `rotation`).
- **Light zones** (`LightZone` in `objects.lightZones`, an optional record: polygon in world px, `ambient` 0–1, `ambientColor?`, `name?`): areas with ambient light of their own, a cave that is dark by day or a lit hall in a dark dungeon. They are map geometry like walls, so undo-tracked and saved with the objects, never part of `SceneLighting`; read them only through `lightZoneList` (`lighting/lightZones.ts`), which keeps their order (later zones lie over earlier ones) and reads the first `MAX_LIGHT_ZONES` (64) that are zones: one that is no area (fewer than three corners, a corner that is no finite number, corners on one line) or has more than `MAX_ZONE_CORNERS` (64) corners is passed over, a hand-edited level is clamped, and a zone's `id` is its key in the record, which is how the store finds it. (64 zones: every zone is a draw of its own with every corner read per texel, about 1.5 s of graphics card time for 64 zones of 64 corners over a whole 8,192 px map and under a millisecond for a room-sized one.) **A map file is validated at reading, never at loading**: the store keeps the file's records as they are (only a `lightZones`, `lights` or `walls` that is no record at all is dropped), so fields of a newer Atlas, surplus zones and objects this Atlas cannot read are saved back, not lost. Lighting and sight read lights, carried lights and walls through `lighting/lightingObjects.ts` (`lightList`, `readLight`, `readEmission`, `readWall`; `wallList` for walls): an object that is no light or wall (no emission, no finite place or ends, a token's `light: "torch"`) reads as none, a `rotation`, `priority` or `sourceRadius` that is no finite number as unset, `darkness` and a wall's `locked` only where they are `true`; an object with nothing wrong reads as itself and a mended one as the same view each time. Never read `objects.lights` or `objects.walls` for lighting any other way. The zone tool begins no zone on a map that holds the maximum and says so (`showZonesFullNotice`). `updateLightZone` takes `LightZoneChanges` (undefined removes a field). *Rule*: `AmbientLight.zones`; `ambientAt(point, light)` is the level of the topmost zone whose polygon contains the point, else the scene's, and `lightLevelAt` reads that, so the polygon is the rule's boundary. `SceneModelBuilder` hands the rule (`model.ambient`, what `ambientLight()` returns, the same object while lighting and zones stay) and the engine (`model.zones`, `EngineScene.zones`, with a soft edge of half a cell) the same list; a lamp that follows the ambient light reads the level where it stands. *Picture*: `ZoneMap` (`engine/ZoneMap.ts`, two world-space `rgba16float` textures, created with the first zone and freed by `LightingWorld.trim`) holds the zones' ambient light premultiplied by their share, drawn onto the floor in order with normal blending (`zoneShader.ts`: the polygon as a uniform array, share 1 inside, falling to 0 over `soft` px past the outline where a sphere trace to the nearest point of the outline is clear, so the soft edge never lies behind a wall and passes a doorway). Like a light's tile a zone ends at a wall's capsule: zone corners are clicked on wall ends, and a share that reached the centre line showed as a bright line to a token in the dark beyond. A capsule has the darkest light that lies on it instead: a second draw fills the capsules alone with the zones darker than the scene, from the brightest to the darkest, each up to `wallBand` past its outline, so a wall a cave ends at is dark through and through and a lit hall's walls are lit only on their faces (the scene's ambient light decides which zones those are, and enters the zone map in no other way, so `LightingWorld.setZones` redraws only when that set changes, `sameZoneLook`: dusk falling over a cave draws nothing anew). *Known tell*: the darkest light lies on the whole capsule, so a token outside a darker zone sees the near half of the wall's core (1.5 texels) as dark as the zone, and the cores of walls that meet that wall from outside, with the corner between them, within two bands of it. Darkening only the capsule's half inside the zone's polygon was tried and is not to be had: sight ends on the centre line and its filtering shows half a screen pixel beyond it, where the scene's light then lies, and bilinear reads carry that light a texel inward, so a token in the dark room sees a lit line along its walls (the zone fuzz: 3,562 pixels brighter than the zone in 9 rooms, 34 with a texel of darkness past the outline), which is the bright line the capsule rule was made against. The composite takes `zone.rgb + uAmbient · (1 − zone.a)` as the ambient light, read at the floor in front of a wall's face like light, and only while `uHasZones` is set (pixel-identical without zones). `lifted` is the same map with each zone's light where dim light is perceived as bright. The soft edge is drawn and not counted, like the fade past a dim radius. Magical darkness swallows zone ambient like the scene's; bounce is untouched; explored memory records the ambient light where it is lit (`ExploredShapes.ambient`: the scene, then each zone in order, lit or dark, painted inside the sight before the lights). `leakFuzzZones.gpu.test.ts` gives every room a daylight zone in a pitch-black scene, a little smaller than the room, on the room's own corners or lying across its walls: nothing lit past a wall beyond 1.5 screen px of filtering, as bright as the day wherever the rule counts it, nothing beyond the soft edge, and a vision token outside the room sees nothing lit at all. A daylight zone is never drawn onto walls, so `leakFuzzDarkZones.gpu.test.ts` gives every room a zone darker than its scene (darkness in daylight, 0.1 in a scene of 0.5): the zone's light wherever the rule counts it and the scene's beyond the soft edge, no wall inside the zone brighter than the zone, a token inside a room that is the zone sees nothing brighter than the zone's light (not a line on the wall), and a token outside sees the scene as it is without the zone up to the wall's core (at a junction with a wall outside, within two bands of the room's wall); its controls are a zone smaller and one larger than its room. *Tool*: the lighting menu's Light zones mode (`WallToolSubMode` `'light-zone'`); `LightZoneEditor` takes every press in that mode (`lightingPointer.ts`): a click places a corner (snapped to a wall end close by, freely with Alt), Enter, a click on the first corner or a double click closes the zone (one undo step; it starts with the scene's own ambient level and no colour of its own, so closing it shows and records nothing new until the GM sets its light in the popover that opens; corners on one line are no zone yet), Escape drops it; a corner is dragged (one undo step; Escape, a cancelled pointer, the window losing focus and the next press put it back and leave none), a click on the zone's handle (`zoneHandlePoint`) opens `LightZonePopover` (store `lightZonePopover`, never open together with a light's; placed by `useZonePopoverPosition`), Delete deletes that zone. The popover is open only while its zone exists and the tool is in zone mode in the GM's view of a loaded scene: `closeStalePopovers` (`popoverGuards.ts`, with `mayEditLight` and `mayEditZone`) closes it on any store change that ends that (delete, undo, another tool, session view, a load), and `LightZoneEditor.stop` when the tool leaves zone mode, its layer is hidden (a peek) or another Obsidian tab becomes active. `LightZoneOverlay` is the `lightZones` layer of `GmOverlays`, shown only in that mode. The Canvas fallback ignores zones (everything in sight counts as lit there).
- **Directional light** (`LightEmission.angle`, 1–360°, unset or 360 shines all around; `LightSource.rotation`, degrees, 0 faces up and turns clockwise like a token's): read the cone only through `beamOf` (`lighting/lightBeam.ts`; a darkness never has one), which is `visionCone` with the light's rotation, or the rotation of the token that carries it (`activeLights`), so a carried beam turns with its token, and sight on drop holds it where the drag began like every other part of the token. *Rule*: `LightReach.cone` clips the reach polygon (`lightReach(..., { cone })`), so `lightLevelAt` counts light only inside the cone; `LightReaches` retraces a reach whose cone changed. *Picture*: the cone is a factor in the light map (`inCone` in `lightMapShader.ts`, uniforms `uCone`, `uSpill`), never in the tile: turning a light traces nothing. Inside the cone the factor is 1, so rule and picture share the cone's edges; past them the light falls off over a width in world pixels, steeply (`EngineLight.edge`, `softEdge`: the fade past a dim radius or half a cell, whichever is smaller; an angle would grow with the distance), and never over more than `BEAM_EDGE` (6 %) of the beam's half-width at that distance (`beamEdge`; of the dark wedge's behind the light for a beam wider than a half turn, so the edge never fills the wedge) and never under one texel of the light map (`BEAM_EDGE_TEXELS`: a narrower edge shows the texels as steps): a narrow or short beam has a narrow edge, as its penumbra grows with the distance. A beam's far end fades over the edge it has there (`beamEnd`) instead of `LIGHT_REACH`, and half a cell around the light (the cone's `apex`), lit all around, over the edge it has at that radius. What is lit past those edges is not counted, and a token standing in it is hidden on a floor that looks lit: `beamSpill.gpu.test.ts` holds that area under 12 % of the counted area for beams from 15° to 355° of every built-in light's radii (10.3 % at worst, a half turn of a light that is bright to its end; an all-round light has 8.3 to 10.6 %), where a fixed edge and a fixed apex fade gave a 15° beam of a 20/40 ft light 55 %. A scene without an angle skips the factor (`uCone.z` is a full turn) and is pixel-identical. `leakFuzzBeams.gpu.test.ts` holds the factor texel by texel against the same lights shining all around (nowhere brighter, nothing outside past the soft edge, all of it inside up to the dim radius), and the leak fuzz lights every other room with beams.
- **Senses are data** (`SenseDefinition`, `types/senseTypes.ts`): what each light level looks like to the sense (`sees`), whether walls stop it (`lineOfSight`), whether it shows the map or creatures only (`reveals`; `showsMap` is `reveals: 'all'` with line of sight, and validation makes a sense through walls creatures-only), `precise` (the token itself, else only its outline), `seesInvisible`, `worksWhileBlinded`, `ignores: 'airborne'`, its `look` (`colour`, `monochrome`, `black-and-white`, `heat`) and how it takes a distance (`range`, `defaultRange`). A modifier (`grants: 'see-invisible'`) perceives nothing itself and lets the token's eyes see invisible tokens. Built-in senses live in `gameSystems/senses/` per system with ids `<preset key>-<sense>` (never change them: tokens store them); read a collection's through `collectionSenses` (its own, else its preset's, else `GENERIC_SENSES`) and a map's through `mapSenseRules`. Normal sight (`NORMAL_SIGHT`, id `sight`) is not a sense a token is given. A token stores `vision.senses` (`TokenSense`: id and optional range); the `darkvision` and `tremorsense` numbers older tokens carry are read as the collection's senses with that `role` (`tokenSenses`), and `withSenses` drops them on the first edit.
- **Statblock senses** (`creatures/`): `tokenSensesResolver(CreatureIndex, mapSenseRulesSource)` answers `visionOf(token)`. A token's senses are its own `vision.senses` (even an empty list), else its old fields, else those `parseSenses` reads from the linked statblock's senses line with the collection's senses and unit; its sight range is its own, else the radius the statblock says the creature is blind beyond (0: no normal sight). While the statblock is unread the answer is `pending` and sight shows and records nothing for the token. Edit Token shows the same through `useStatblockSenses` (`inheritedSensesOf`), so the editor and sight cannot disagree. `SightRulesWatch` holds a view's `SightRules` (definitions, conditions, `visionOf`) and compares them again when the collection's settings are saved, Atlas' settings change (a user preset), the asset index has loaded or the resolver announces a statblock; it asks for a rebuild, once per frame however many arrive, only when the rules differ in what sight goes by (`sameSightRules`), so a homebrew sense saved in the Vision tab or a deleted one reaches an open map at once and other saves build nothing.
- **Sight is token-based**: the local player picture uses every vision-enabled token that is not hidden (`tableSightSource`). Hidden tokens contribute no sight, footprint or new explored memory. `SceneModelBuilder` computes GM regions once, including hidden vision tokens, then `tableSight` selects the player regions without tracing again. The GM map shading and selected-token range rings keep their prior sight (`gmSightSource`); the GM's visibility marks describe the corrected player picture. If every vision token is hidden the player picture gets `NO_SIGHT`; only no enabled vision token, or token vision switched off, gives `SEES_ALL`. Blinded or pending sources do not open the map. `SightCache` eviction belongs to each real model build (Canvas fallback included), using all its source IDs; `computeSight` never evicts. Held-for-sight positions and the held footprint restriction remain unchanged.
- **Vision cone** (`vision/visionCone.ts`): `TokenVision.angle` (1–360°, unset or 360 sees all around) faces the token's `rotation`, which follows the renderer: 0 faces the art's up, positive turns clockwise on screen, so the world angle is `rotation - 90°` (`visionCone`). `computeVisibility(..., cone)` sweeps the full circle, then `clipToCone` keeps the vertices inside and closes the polygon through the origin with the two cone edges, ending where they cross the outline, so it stays star-shaped. Every sense of the eyes (one that does not work while blinded) is clipped by the same cone; the others reach all around. The cone edges are hard: `sightWedges` skips radial edges that start at the viewer, so only wall corners get a penumbra. `SightCache` also keys on the cone, so turning a token recomputes its sight.
- **Perception** (`vision/perception.ts`): `perceive(point, sight, level, target)` is `seen`, `sensed` or `unseen`: a region perceives the point when it contains it, its sense sees at the point's light level and the target's conditions do not rule it out; a precise region wins (`seen`), and only where none perceives it an imprecise one counts (`sensed`). It asks the cheap questions first (target, radius, light level, polygon). `tokenPerception` (`pixi/lighting/playerLightingLayers.ts`) answers per token for lighting (`playerTokenSight`); `PlayerSightTokens` composes committed fog separately for presentation; a `PerceptionMemo` keeps the answers while sight, light, conditions and held tokens are the same objects. A nonhidden token with vision is always seen, subject to the held-for-sight restriction; a hidden target is always unseen, whether or not it has vision. A sensed token is hidden like an unseen one and drawn as an outline above the lighting (`SensedOutlines`, through `PlayerSightTokens`), without art, nameplate or bars.
- **Conditions change sight** (`ConditionDefinition.effect`: `blinded`, `invisible`, `airborne`, `undetected`, or `none` to switch a built-in condition's effect off). Read it only through `conditionEffect` (`gameSystems/conditionEffects.ts`), which also knows the built-in conditions that collections copied before effects existed, by their ids.
- **Footprints** (`seenSpots`): where no sense shows the map around a token that is shown (a party token in darkness; a token only a precise creature sense sees), the token is drawn within its own footprint, clipped by the walls it stands at (`computeVisibility` from its centre), so nothing shows past a wall's centre line except through a one-way wall from its open side, as sight does. None for a held token beyond the sight it left behind, for a hidden token, or while `sight.all`. `SceneSpots` keeps the list while it is unchanged.
- **Sight on drop** (`SceneLighting.sightOnDrop`, unset off; `lighting/sightOnDrop.ts`, read with `sightOnDropOn`): by default sight and light follow a token while it is dragged: its sight, the light it carries, explored memory, the players' picture and the GM sight aids are rebuilt at every step of the drag, which costs what any token move costs (`SightCache` recomputes the moved token, `LightReaches` and the tile cache its carried light; `tests/gpu/liveDragCost.gpu.test.ts` prints the cost per step). The lighting panel stores `true` for a scene that waits for the drop and removes the field otherwise. The rest of this bullet is what happens with it on. `InteractionController` notes the tokens the pointer holds, each with the place it was taken from, in the store's `heldTokens` (`holdTokens`; UI slice, so never saved and never an undo step; noted whatever the option says, `heldForSight` returns none while it is off), and both lighting views read their tokens through `SightTokens`, which keeps every dragged token at that place until release. A drag then shows, lights and records nothing along its way and costs no lighting work (`SightTokens` returns the same record while only held tokens move, so `SceneModelBuilder`, which builds the scene's lights, reaches and sight for `LightingRenderer`, builds nothing), and the drop rebuilds once; the store itself follows the drag, moves that are not drags are read as they are, and since there is one light map the GM's canvas waits for the drop too. A pointer that is lost (`pointercancel`, the window losing focus) drops the tokens where they are. In the players' frame a dragged vision token shows only in the line of sight that stayed behind (`tokenPerception` with `heldForSight`: `seen` only `withinReach` of that sight, by any sense, lit or not): beyond it the token goes with its nameplate, bars, conditions and drag ruler, which would otherwise stand over the darkness that covers its sprite.
- **Default vision** (`SystemRules.defaultTokenVision` / `CollectionSettings.defaultTokenVision`, `TokenVisionDefaults`: range, angle, senses): a token placed from the library starts with `vision: { enabled: false, ...defaults }`, stamped once by `tokenSpawnService` from the placing map's collection (`mapVisionDefaults`). A token that links a statblock gets no default senses, so it follows the statblock. It is never stamped on encounter tokens restored from a saved snapshot, never updates placed tokens later, and never switches vision on. Read it only through `gameSystems/visionDefaults.ts`: `parseVisionDefaults` keeps distances above 0, an angle of 1–359 (360 is all around, so it is dropped) and the senses the collection defines, and drops anything else (an empty default is no default), `sameVisionDefaults` compares. Built-in presets set it only where every character of the system has a baseline (none do today). The Vision tab of the collection settings edits it and the collection's senses (`SensesEditor`, `react/components/senses/`, the same list editor Edit Token uses).
- **Scene options** (`SceneLighting`, read through `lighting/sceneLightingOptions.ts`; edited in the "Lighting settings…" panel, `SceneLightingPanel`, from the lighting dropdown; never undo steps): `tokenVision` (unset on), `exploredMemory` (unset on), `exploredColor` (unset `#ffffff`, tints remembered areas), `unexploredColor` (unset `#000000`, fills what was never seen), `litThreshold` (unset 0.25), `brightThreshold` (unset 0.75; no control yet), the editable `ambientColor` (unset white), and `darkSightLook` (`system`, `grey` or `colour`; unset `system`) with `darkSightTint` (unset none). Unset options are pixel-identical to the composite before they existed. The last two change only how the composite draws what a sense with a look without colour shows in the dark (the green channel, `darkLooks`), never what is perceived or recorded, and never the senses that see in colour: `system` is each sense's own look, `grey` draws every such look (monochrome, black and white, heat) in the grey of darkvision and `colour` in the map's own colours, each at the level the sense sees the dark at; the tint gives whichever look applies its hue and leaves every pixel as bright as it was: `darkSightTint` (`senseDrawing.ts`) hands on the picked colour's hue alone, and none below a small chroma (greys, near blacks), and `tinted` in the composite scales the tinted colour back to the pixel's own luminance, letting the hue give way to white where one channel cannot carry it (a pure blue on a pale floor). A tint therefore never changes how much the party sees, on any floor (`darkSightLooks.gpu.test.ts` holds it within 15 % over floors, tints and looks), and a tinted sense never falls below the remembered look, so none of that is mixed in. The panel stores the system's look and no tint as unset: `setSceneLighting` takes `SceneLightingChanges`, where an option given as undefined is removed. Read them with `darkSightLookOf` and `darkSightTintOf`, which read a value they do not know as unset. Token vision off makes `sceneSight` return `SEES_ALL`: players see everything the light shows and nothing is recorded. Explored memory off records nothing and shows none (`setMemoryShown`), but keeps and saves the mask it holds, so switching it back on restores it. `litThreshold` is the ambient level from which everything in sight counts as lit, the boundary between dark and dim (`ambientLevel`, `exploredShapes`); the panel commits it on slider release, since every step would rebuild sight and a pass below the ambient level would record all in sight for good. `LightingRenderer` rebuilds the scene when these options, or the ambient crossing the threshold, change. Read colours through `readSceneLighting` (drops values that are not `#rrggbb`, and a darkvision look that is none of the three).
- **CPU**: `visibility.ts` is a radial sweep; `SightCache` recomputes only moved tokens or after the walls reference changes, `LightReaches` (`pixi/lighting/lightReaches.ts`) each light's reach only when it moved, its reach changed or the walls changed. `SceneModelBuilder` (`pixi/lighting/sceneModel.ts`) builds lights, reaches and sight only when their inputs change; the sight rules count by identity, so keep the definitions list the same object while nothing changed. `tokenPerception` decides which tokens (and their nameplates and bars) the player frame hides.
- **Walls as the engine sees them**: walls are never moved; gaps up to ~13 px at 2 px texels are sealed for light and sight alike. `sealedWalls(walls, worldTexel(bounds))` (`lighting/sealWalls.ts`) adds a solid bridge wall between wall ends within `sealTolerance(texel)` of each other and from a wall end across a nearby wall's middle (T-junctions stopping short); light, bounce, sight, light reach and the Canvas fallback all read the drawn walls plus these bridges, so a joint is closed for all or none. The bridges grow with the wall ends, not with their pairs (a damaged or foreign map with thousands of ends in one place made millions and never opened): ends that share a point are one junction, and a junction with more than eight others within the tolerance is bridged to the nearest in each of eight directions only, which closes the same gaps (from A towards any B the nearest in B's direction is nearer to B than A is, so a chain of bridges leads to B inside the circle around B that A lies on; the chain may run along a wall between its own two ends only where that wall stops everything, so the other end of an open door or one-way wall is passed over for the next nearest, and where the nearest in a direction is an end of such a wall standing on its own, the wall's other end is bridged from there too (`loneMate`: it may be the very end the chain was to reach, and two such walls facing each other between crowded ends were left unjoined); `sealWalls.test.ts` checks the chain for every pair, `junctionSeal.gpu.test.ts` light and sight at a hub of up to 24 walls); an end that more than eight walls pass is bridged across those that reach farthest: the ones whose landing is a corner of the convex hull of the end and all its landings (a ray is stopped by an end's bridges exactly when a landing lies beyond it, and whenever one does a corner of the hull does; the eight nearest are not enough: nearer walls then left the gap to a farther one open; the corners are kept as the walls are met, so an end holds a handful of landings however many pass it), and an end with more than twelve such corners, or that more than 64 walls pass, is closed off whole (`plugs`, `lighting/sealPlugs.ts`): a polygon of sixteen bridges that holds every landing the end's own bridges could have, shared by the ends that lie in one eighth of a pixel. It reaches 0.45 px past the tolerance at its corners and no nearer than the tolerance anywhere, so it stops all that the end's bridges would; it cannot stay within the tolerance and do that, the landings lying up to the tolerance away on every side. So at most eight bridges are begun at a place, eight more to the far ends of walls on their own, and sixteen across the walls that pass it (64 tangent walls around 40,000 ends made 2.6 million bridges and now make 40,000). `sealWallsRays.test.ts` holds the capped bridging against a bridge for every pair (`sealAllPairs`) with rays through junctions of many kinds: none may pass that all pairs would stop. Junctions are looked up in `PointTree` (`lighting/pointTree.ts`), a k-d tree with a box per node: an end's neighbours are sought only until every direction a node reaches into holds a nearer one, the ends beside a wall without stepping along it, and a node whose ends are all closed off is never opened again, so 20,000 walls piled into a few pixels or 8,000 walls passing 8,000 ends seal in well under a second (`sealWallsCrowded.test.ts`). A node also keeps the bounds of its points along both diagonals (x + y, x − y): the eight directions meet on the diagonals through a point, so the boxes of ends along a 45° line reached into the empty direction beside them and none was ever passed over (20,000 walls on one diagonal took 7.5 s); the two directions of a quarter are told apart by those sums, for nodes and points alike (`steeper`), and a node is no nearer than its box or its diagonal bands. Its quickselect takes the pivot anywhere in the range by a fixed sequence, not the middle point, which is the least of what is left time after time where two sorted runs follow each other (two strokes side by side built in the square of their length). `sealWallsHostile.test.ts` holds such inputs to seconds and `pointTree.test.ts` holds the tree against looking at every point. Walls are capsules of `wallRadius(texel)` (at least a texel diagonal) in a world-space `r16float` distance field (`engine/CapsuleField.ts`, instanced quads, `min` blend). Shaders read it conservatively (`fieldGlsl`: minus 0.75 texel for bilinear, shrinking outside the field) and sphere-trace with steps never longer than the clearance (`TRACE_GLSL`), so no path can jump a wall; out of steps counts as blocked. This is the leak-proof guarantee; `leakFuzz.gpu.test.ts` enforces it.
- **Walls that block one thing** (`WallSegment.blocks?: 'sight' | 'light'`, `WallChannel`; unset blocks both, as every wall did): a curtain stops sight and lets light through, glass that glows stops light and lets sight through; a door keeps its kind, and a one-way wall is one-way for the thing it blocks. *Rule*: whoever asks what a wall stops names the channel. `computeVisibility(origin, radius, walls, cone, channel)`, `blocksFrom` and `splitBlocking` leave out the walls that block only the other thing (`concerns`, `lighting/segments.ts`): sight, footprints and every sense with line of sight ask for `'sight'` (`regionsOf`, `seenSpots`), light reaches and so `lightLevelAt`, darkness areas and what a darkness quenches ask for `'light'` (`lightReach`). Without a channel every wall counts whatever it blocks, so a caller that forgets is stopped by more walls, never by fewer; never filter a wall list by hand. The sealed walls stay one list (`SceneModel.walls`, `EngineScene.walls`), so the caches keyed on it are untouched and a scene without such walls decides exactly as before. *Picture*: `WallFields` (`engine/WallFields.ts`) holds the map's fields: `tiles` (two-way solid walls that block light: what a light's tile is traced through, with the one-way walls that block from its side in the light's own field), `light()` (every wall that blocks light, one-way and limited ones too: bounce, the composite's wall faces and bounce gather; `zones()` is the same without limited walls, for the ambient zones) and `sight()` (every wall that blocks sight: the explored memory's blur, `exploredAt`). The composite reads two fields, `uField` and `uSightField` (`fieldGlsl`, `traceGlsl`, `wallPushGlsl` take the field's name; `CapsuleField.resourcesAs` binds a field under another), which are one texture bound twice unless a wall of the scene blocks one thing only: the third field exists while such a wall does, as the second while there is a one-way or limited wall (`WallFields.trim` frees them once the composite has taken the fields that are left). Sight itself is the CPU polygon, so the sight meshes need no field. A wall for one thing is in the fields of that thing alone, so each field's leak guarantee is the plain one over its own walls: `leakFuzzKinds.gpu.test.ts` gives every room walls of one kind and chains of the other across it, and holds each picture against the scene with only that channel's walls in it as plain walls (light, sight, memory: no pixel differs), besides no light past glass, no sight, sense, footprint or memory past a curtain, and the rule asked at sampled points. *Sealing*: a bridge blocks the one thing the walls it joins all block, else both (`shared`, `lighting/sealKinds.ts`), a curtain's joint with glass too: for either channel every joint of two walls that block it is closed for it, and a bridge that blocks more than its walls only ever closes more. Bridges at a place bridged to fewer than all its neighbours, the capped bridges across passing walls and the plug block both, because the chains and hull corners that stand in for the missing bridges lead over walls of any kind; a short wall that blocks one thing is not counted on to close a gap between two crowded ends (`endsOfOneOpenWall`). *Editing*: the wall menu's Blocks (Sight and light, Sight only, Light only; `showWallMenu`) changes every selected wall through `WallInteraction.updateSelected`, one undo step; `updateWall` removes a field given as undefined. `wallKindLook.ts` draws such a wall in its own look, long dashes for sight only, dashes and dots for light only, in screen pixels on a dark casing, in a layer of its own (`KindWallLayer`) that draws anew when the zoom changes: only the parts of walls on the screen and half a screen around it, once in the frame's tick however many zoom events it brought, coarser alike where the screen holds more than 12,000 strokes and dots, and after a pan only once the screen leaves what was drawn (20,000 such walls: 9 to 70 ms a zoom step; all of them at every event took up to 3.4 s). A door placed in such a wall keeps the kind; a secret door of a kind keeps its colour and is drawn hollow (a dark middle in its strokes and dots). *Files*: `readWall` reads a `blocks` that is neither as a wall for both and leaves the record as it is. The Universal VTT import makes no such walls (its windows stay skipped).
- **Limited walls** are **switched off** (`LIMITED_WALLS = false`, `src/app/featureFlags.ts`) and not part of the release. `readWall` (`lighting/lightingObjects.ts`) is the one place that decides it: with the flag off no wall reads as limited, so a wall whose file says `limited: true` (a hand edit, a later version) blocks and looks like any wall, its field stays in the file, and none of the code below runs (no count, no crossing rays, no tile mask, no extra field, no dotted look); the wall menu offers no Limited switch (`showWallMenu`). `limitedWallsOff.test.ts` and `limitedWallsOff.gpu.test.ts` hold a scene with limited walls to the same scene with solid ones: the same bridges, sight and light, and the same picture pixel for pixel. The limited-wall tests and fuzz families still run: they hand limited walls to the code directly, and those that go through `readWall` mock the flag on. **Do not switch the flag on before the review's open points are closed**: the rule that joins limited walls within 13 px into one hedge is unsafe (it shows what two drawn hedges must hide: beside an X, behind hedges side by side, behind a room wall just inside a garden hedge); light survives past two hedges in a solid wall's soft shadow where the second hedge ends inside that shadow; two limited walls met at the same distance are told apart by rounding; and a viewer or light standing exactly on a hedge sees hairlines. The plan is strict counting (every drawn limited wall counts one, a sealing bridge is the hedge in its gap only, a light's tile is held to what points of its flame reach), begun on the branch `experiment/limited-walls`. What follows describes the code as it is behind the flag. (`WallSegment.limited?: true`: a hedge, a low wall, a fence; Foundry's terrain walls): sight and light pass the first limited wall on their way and stop at the second, so what stands at a hedge or right behind it is seen and nothing through two; a solid wall stops them as ever. *The table*: for a channel (sight or light) a wall is **nothing** when it is an open door, has no length, blocks only the other channel (`blocks`), or blocks one way and is met from its open side; else it is **limited** when `limited` is set and **solid** otherwise. So a limited closed door is limited and opens like any door, a limited wall with `blocks: 'sight'` is limited for sight and no wall for light, and a one-way limited wall counts only from its blocking side. *Rule*: the sweep (`visibility.ts`) stops each ray at the nearest solid wall or at the second limited wall it crosses, whichever is nearer (`vision/limitedRays.ts`: `limitedHit`, `secondCrossing`), counting in the order the ray meets them; a scene without limited walls in reach is swept exactly as before. Where a limited wall crosses another wall between their ends the two swap their order along a ray, so the sweep casts a ray at every such crossing too (`limitedCrossings`): without it the polygon's edge from one side of the crossing to the other cuts behind both walls. `vision/__tests__/byHand.ts` is the reference the tests hold the sweep and the pictures against: every crossing of a straight way counted, a solid wall or the second limited one stops (`limitedCrossings.test.ts`, `leakFuzzLimitedShapes.gpu.test.ts` for the shapes the rooms of `leakFuzzLimited` never make). **Limited walls that run together are one hedge** (`vision/limitedJoins.ts`): two limited walls run together along the stretch of each that lies within `LIMITED_JOIN` (13 px, the seal tolerance at the base texel) of the other, and a ray that meets both within those stretches has met one hedge: the two walls of a corner for a ray through it or close by it, strokes of a row that end short of each other, past each other or over each other, the bridges of a sealed joint, two hedges drawn side by side nearer than that. So a corner is never a hole and never counted twice, a row drawn in several strokes casts no dark stripe behind its joints, and a ray that cuts a corner's tip by less than the join passes it as its neighbours beside the corner do. Two walls that cross as an X (between their ends, every end farther than the join from the other wall) are never one: what lies behind both stays behind two. A hedge counts from the first wall a ray meets: walls that run together with that one are it, the next that does not is the second. The stretches are fixed by the walls, so the count changes only at their ends, where the sweep casts rays as at wall ends (`LimitedJoins.points`). On a map with coarser texels the sealing bridges wider gaps than the join; a ray through such a joint may count two (it errs towards stopping). Light reaches, footprints and every sense with line of sight are that sweep (`computeVisibility`), so `lightLevelAt` and `perceive` follow. *Picture*: sight is the CPU polygon as always. A sphere trace cannot count the walls it crosses, so a light's tile is traced through solid walls only (`splitBlocking` keeps limited walls apart, `solidSegments` leaves them out) and `LimitedTileMask` (`engine/LimitedTileMask.ts`, called by `TileCache` for every light a limited wall stands in reach of) takes out of the finished tile what limited walls stop: everything beyond the polygon of `sweepLightMask` (along every ray from the light's place, as far as the first limited wall, and behind it only as far as the rule's own reach), in strips that overlap a little so that no sliver thinner than the rasteriser's grid stays lit; a box a capsule's width around every edge of that polygon that lies on a limited wall; and, around every limited wall, each texel takes the darkest of itself and what lies across the wall (`limitedShader.ts`, into a new tile), because a ray along a wall that stops elsewhere lights the floor beside it though the wall's other side is dark. **Behind a limited wall a light is exactly the rule's reach**, hard-edged, a single hedge with a wall behind it too: a soft shadow there is light from the flame's edge that passed a solid wall's end through limited walls the count from the flame's middle never met (it lit the floor past a second hedge in the soft shadow of a wall the first hedge joined). Before the first limited wall on a ray the tile is what it is in any scene, with the soft shadows of solid walls; the shadow a limited wall's end casts is hard. Every other reader takes a limited wall for a wall: `WallFields.light()` and `sight()` hold them, so the composite gives a hedge's near face the light of the floor before it, the explored memory's blur does not cross one, and **bounce does not pass a limited wall** (it is a little darker behind a hedge than the rule's light alone would make it; nothing is lit that the rule counts as dark). An ambient zone is the exception: it is drawn through `WallFields.zones()`, the walls that stop light without the limited ones, so its soft edge passes a hedge as light does and the zone lies on the hedge's own line (a wall's capsule is left out of a brighter zone, which made a hedge in a lit clearing a black line). A darkness is the rule's polygon and so passes the first and stops at the second. A scene without limited walls builds no mask and no extra field. `leakFuzzLimited.gpu.test.ts`: every wall of a room limited, a second ring around it limited or solid in turn; no light, sight, darkvision, footprint, memory or darkness past the ring except where counting by hand lets it (the ring running together with a wall of the room), lit and seen between the room and the ring, and the rule asked at sampled points; `leakFuzzLimitedShapes.gpu.test.ts` holds the light map and the players' picture against the count by hand for hedges that cross, a hedge joining a solid wall's end, and rows of strokes; `limitedWalls.gpu.test.ts` scans the light map itself for a lit texel beyond a ring. *Sealing*: a bridge is limited only between limited walls (and one hedge with them, as above) and solid where a hedge meets a wall, at a crowded place and across many passing walls (`shared`); a short limited wall is not counted on to close a gap (`partsNotAll`). *Editing*: the wall menu's "Limited (see past the first)" switches every selected wall, one undo step; `wallKindLook.ts` draws a limited wall as a row of dots, in the groups of its dashes where it also blocks one thing only; a door placed in one stays limited (`keptByParts`). *Files*: `readWall` reads `limited` only where it is `true`.
- **Direct light**: `placeLight` moves a light standing in a wall to the nearest free spot reachable without crossing a centre line and fits its flame into the free space. Each light has a cached `r8unorm` visibility tile (`TileCache`, `tileShader.ts`: cone test, else 32 equal-area jittered rays to the flame), rebuilt only when it moves or walls within `tileWallReach` of it change (`changedWallRects`). A second pass (`tileSmoothShader.ts`) melts the 1/32 ray steps: each texel becomes a Gaussian average of the texels closer than its clearance (at most `TILE_SMOOTH` texels), a disc that holds no wall, so light spreads only within free space and contact shadows stay crisp. There is no contact fade: a tile is lit wherever the trace clears the capsule and exactly 0 where it fails, and the composite lights the capsule's edge (wall faces, below). Raw traces go to two targets used in turn, so a trace never waits for the previous tile's smoothing, and the tracer frees them once an update rebuilds no tile (a dragged light rebuilds on every update, and allocating per rebuild cost about 40%). Tile rects sit on the light map's texel grid and are read with `texelFetch`, so only one bilinear step ever spreads light, and the wall radius covers it. `LightMap` accumulates all lights into a world-space `rgba16float` texture, redrawn on changes and for flicker at most every `FLICKER_INTERVAL_MS` (about 30 times a second: the walks step every 45–120 ms and are interpolated), never per camera. Flicker changes intensity and the bright radius only: moving a flame would shift its tile past walls, and the dim radius is where the rules end the light.
- **Falloff** (`engine/lightMapShader.ts`): the picture shows the rule (`lightLevelAt` counts everything within the dim radius as lit, bright within the bright radius). A light gives `LIGHT_LEVELS.bright` up to its bright radius and `LIGHT_LEVELS.dim` from there to its dim radius, joined by a knee, `dim + (bright − dim) / (1 + (d / brightRadius)⁴)`, that is halfway down at the bright radius; from the dim radius it fades (smootherstep) to exactly zero at `LIGHT_REACH` × dim, kept short because the rules count nothing there (at 1.06 a candle looked cut out). `LightRangeRings` draws those two radii. The tonemap's toe squares low values, so on a dark map dim light showed far below its share of bright light: the light map's alpha holds the luminance each light would have at its bright level, and the composite tonemaps at that level and scales the result back (`lift`; exactly 1 without a light, so unlit pixels are untouched). `lightFalloff.gpu.test.ts` measures what the players see, the displayed luminance of the floor at ambient 0 after exposure and tonemap: nowhere in the dim range under a quarter of its value halfway to the bright radius (about a third on floors from #404040 to white and at any intensity), falling only with distance, never steeply, and keeping its colour through the fade. Never let the dim range fade before its edge, and never let flicker move the dim radius (a moving edge). The floor's bounce (`BOUNCE.floorGain`) is tuned to that much lit floor: past the reach it stays under a fiftieth of the bright level on a mid-grey floor.
- **Glow**: each light adds a Gaussian halo (`HALO`) to its falloff inside the light map, before the tile mask, so it stops at walls. There is no bloom filter: an image-space blur crossed walls, as the fuzz showed.
- **Bounce**: `RadianceCascades` (world space, bilinear fix per child direction, so each path is a chain of traced segments), rebuilt at most every 100 ms while lights change; the composite reads only probes a pixel has a clear path to. Albedo is the map colour weighted by its alpha, so maps without an image (or transparent PNG parts) bounce as mid grey. One-way walls block bounce both ways.
- **Sight on the GPU**: `SightMeshes` draws each region's polygon as a fan in the lighting layer, softened only inward by penumbra wedges (`sightWedges`), into four channels (`engine/senseDrawing.ts`, blended with `max`): red = seen by the light there, green = perceived without light in the scene's look without colour (`monochrome`, `black-and-white`, `heat`), blue = perceived without light in colour, alpha = dim light drawn as bright (low-light vision). Regions that share a polygon share one mesh with their channels merged, and the mesh of a token that did not move is kept, so three senses cost what one does. The composite shows the brighter of what the light gives and what a sense gives (`brighter`); the look without colour is one per scene (`darkLooks`). Footprints are drawn hard-edged into red and blue (`drawSpots`). Only senses that show the map are drawn (`showsMap`); creature senses change which tokens show, never the picture. A scene without such senses or footprints is pixel-identical to the composite before senses (`memoryComposite` hashes). Being in the scene graph, it follows each render's camera, including the player window's. `SceneSightLayers` keeps a second set of meshes only when GM and player sight differ; switching frame mode reuses geometry and switches sight channels, dark-sight look and magical-darkness piercing together. A thumbnail forces GM sight and restores the selected frame even if its render throws. The light list is unchanged between these frames. The CPU polygon already reaches each wall's centre line, so the composite adds no reveal: the near half of a drawn wall shows, the far half never (the leak fuzz allows sight, senses and footprints only 1.5 screen px of filtering past a centre line).
- **Deviations from the smoothing addendum** (`docs/plans/2026-09-30-dynamic-lighting-engine-v2-smoothing.md`, fix round 1): the band is capsule + one texel, not capsule + two; bounce is read at the same point as direct light, with the same weight; the face blends back to its own light over the texel after the band, not from the core (blending from the core left a dark line along walls); there is no sight reveal, so `REVEAL` is gone; the raw targets are freed when an update rebuilds no tile, not after every batch.
- **Wall faces** (`engine/wallPushGlsl.ts`): tiles end at the capsule, so a pixel between `wallCore` (1.5 texels) and `wallBand` (capsule + one texel, where the light map is fully lit again) from a centre line takes the direct light and bounce of the floor in front of it, then blends back to its own light over the next texel. `climbFromWall` walks up the wall field, taking the gradient anew at every step, until the conservative distance reaches the band, so it bends out of inside corners rather than sliding into another wall's shadow; every step stays inside the ball the conservative field proves free of centre lines, so the point read lies on the pixel's side of every wall. Nearer than the core a pixel keeps its own light. Sight is never pushed.
- **Composite** (`engine/compositeShader.ts`, `blendRequired`): linear albedo × (ambient + direct + bounce), PBR Neutral tonemap (a light's own light at its bright level, see Falloff), cool grey where the light is low by the share that is ambient or bounce (shifting a light's own fade drew a pale ring around it), player/GM modes. One layer (z 90, above tokens, below token UI); A view created while dynamic lighting is switched on draws through PIXI's back buffer all the time (`useBackBuffer`, `PixiAppManager`'s `throughBackBuffer`, decided in `RendererService.init` once the settings are read): PIXI then gives the canvas no samples and the back buffer carries the antialiasing (an antialiased canvas under a back buffer was 190–250 MB of samples nothing drew into). Other views keep an antialiased canvas, since unlit the back buffer costs about 80 MB more than samples on the canvas. `LightingEngine.setEnabled(on)` holds the back buffer (`BackBufferHold`, `engine/backBuffer.ts`; on a renderer without `useBackBuffer` the hold switches it on and off): from renderer resolution `PLAIN_BACK_BUFFER_RESOLUTION` (2) lighting makes it plain (a 4× back buffer at Retina size cost two to three times the GPU time per lit render), and it is multisampled again when lighting goes; a back buffer texture that no longer fits is destroyed with its source. The world textures exist only while lighting is on. Nothing renders inside the main render, nor inside PIXI's `contextChange` runner: world textures update from store changes and the ticker, like `ExploredTexture`, and a restored WebGL context is only noted there and rebuilt from the last scene at the next update or tick.
- **What the lighting does not light**: the composite lights everything beneath it (z 90) like the floor, so a layer left at zIndex 0 sinks into the dark with the map. Marks and tools stand above it, below the token UI, at `MAP_LAYER_Z` (`pixi/mapLayerOrder.ts`): note pins, hex-link highlights, the ruler and measurements, the selection frame and marquee, text handles and the text preview, the grid alignment tool's marks; text (500), drawings (900), fog, walls and the laser already did. Give any new mark or tool a place there. The GM sees it everywhere, the players where a light or a sense shows them the map now or they remember it, never over what they have not seen; an automatic colour (picked against the lit map) is white where the ambient light (the scene's or a zone's) is below `GRID_DARK_AMBIENT`, and lights never change it: following the light at each pixel shaded the grid through every light's fade. Without the composite (lighting off, failed, the Canvas fallback) the grid is never marked, since a marked grid would erase the map under its lines. `unlitGrid.gpu.test.ts`.
- **Engine shaders** are listed in `engine/engineShaders.ts` (`ENGINE_SHADERS`) and created only from those entries (`createShader`, `engineProgram`), so the rules below and the device check cover every program; `engineShaders.test.ts` enforces both rules.
  - *PIXI's uniform names are reserved.* PIXI sets them itself, with its own types, on every shader that declares them: on a `Mesh` `uTransformMatrix` mat3, `uColor` vec4, `uRound` float, `uProjectionMatrix` mat3, `uWorldTransformMatrix` mat3, `uWorldColorAlpha` vec4, `uResolution` vec2; on a filter `uInputSize`, `uInputPixel`, `uInputClamp`, `uOutputFrame`, `uGlobalFrame`, `uOutputTexture` (vec4). Another type is a GL error on every draw (the light map's colour is `uLightColor` for that reason).
  - *No implicit gradients*: never `texture()`, always `textureLod(…, level)` or `texelFetch`. ANGLE translates to HLSL for Direct3D, whose compiler rejects or unrolls loops and branches that sample with implicit gradients. Engine textures have no mipmaps (level `0.0`); the map image has them up to 2048 px, so the bounce's emission pass names the level an emission texel spans (`uAlbedoLod`).
- **Lighting never takes the map down.** `LightingEngine` asks the driver whether its shaders link before it draws on a context (`failedEngineShaders`, once per context, logging name and driver log), draws nothing while the context is lost, and stops for good (`failed`: layer hidden, world and back buffer released) when a pass throws; engine constructors draw nothing, so a stop always finds the world whole. `LightingRenderer` sends every call that reaches the GPU (store updates, ticks, explored stamping and saving, the decoded mask) through `run`, which reports `onUnavailable` instead of letting an error reach the store, the ticker or PIXI. While `isMapLoading` it treats lighting as off: a load rewrites the store in steps (the next path, a cleared scene, the saved one), and the update that ends the load builds the scene whole. The player window shows none of this: `PlayerFrameMirror` holds its frame for the load. `LightingController` holds a `LightingViewHost` (`createSceneLighting`): it swaps the engine's view for `CanvasLightingFallback` behind one stable `SceneLightingView` (the players' view, `modeLayer`, and the sight carry over), tells the GM once with a `Notice`, and never lets the fallback write explored memory. After `failed` the view stays on the fallback for its life.
- **Crash marker** (`lightingAttempts.ts`): a graphics process that dies during a build takes that handling with it, so the map's path is noted in the vault's local storage (`app.saveLocalStorage`, device-local, never synced) before the engine's first build and removed once the graphics process has executed its first lit frame (the tick after that render calls `gl.finish()`, the next one, which a lost context skips, removes the note), or when lighting goes off, the map unloads or the engine fails in an orderly way. Attempts are counted per path: a note stays until the last view attempting the map is done, and an attempt cut short keeps its note for every later start. A note found at a start, or an attempt begun again after a lost context, is `unfinished`: the view goes to the fallback with the notice (once per map). Only the GM forgets a note, by switching dynamic lighting off outside a load. Every map load passes through lighting off too (`clearMapState`), so a load only brings the engine's view back and `begin()` decides for the map that arrives.

- **Explored memory**: a world-space render texture (≤2048 px), saved as a PNG data URL at its own size in the map's `exploredMask` (`saveExploredMask`), validated on load (`readExploredMask`). The GM sees every light at full strength wherever it reaches; what no token sees keeps its brightness and loses part of its colour (`UNSEEN_FADE` in the composite). The initiative list is not part of this: it never follows sight (Initiative, below).
- **GM sight aids** (`GmSightAids`; its rings and marks are one `GmOverlays` layer, so never in the players' view, a peek or a thumbnail): on a lit scene in GM view, `SenseRangeRings` draws the ranges of up to four selected vision tokens (a solid ring for sight, dashed for senses that show the map, dotted for creature senses, arcs and the cone's edges where the token looks one way, each labelled with the sense's name and its distance as it is set (`formatReach`: 7.5 m is not 8 m); they show reach, not what walls leave of it; what has no limit has neither ring nor label (Edit Token says it), and a cone's edges then run to the map's diagonal; none while the scene has token vision off; dashes keep one length on screen, and a ring too long to dash all around is dashed only where the screen shows it; drawn anew only when the selected tokens, the zoom or the theme change), and `PlayerSightMarks` puts a small badge on every token the players do not see (an eye struck through, or a dashed circle for one they only sense; hidden tokens carry their own mark). A badge's circles and the sensed glyph are drawn `DRAW_SCALE` times larger and scaled down, like the resource wheels, and the eye is a sprite of one white, mipmapped 192 px texture tinted in the theme's ink (as `HiddenTokenIcon` and the condition glyphs), never `Graphics.svg()`, whose curves show corners once the map is zoomed in. The marks rest at `restingTokenUIScale` and do not grow with a selected token's UI. Both follow the store and `onSightChange` in one update per frame. There is no line about sight on the token hover card: the players' view and the marks say what is seen.
- **Light markers** (`LightMarkers`, look in `lightMarker.ts`): one badge per placed light, in the pins' language and smaller (radius 14): the theme's badge (`canvasBadgeColors`), the glyph of the light's kind (`lighting/lightGlyphs.ts`, game-icons.net; they are not pin icons) and a thin ring, both in the light's colour (`readableTint` moves it until it contrasts with the badge). A switched-off light is dimmed, a selected one (lighting tool, or its popover open) ringed in the theme's accent, hover and drag lift it. It is the only marker of a light: shown in a lit scene and with the lighting tool, at the pins' size on screen (`mapMarkerScale`), never while the canvas shows the players' view (`setSuppressed`). `lightMarkerAt` is the one hit test. A light's kind is `emission.kind` (`lightKindOf` reads lights without one, or with one not in `LIGHT_KINDS`, by the preset they equal, else as custom); editing its values keeps it. A theme change redraws every badge (`Marker.theme`), also one whose look is unchanged or that was hidden then. A light with a beam grows a tip on its badge the way it faces (`LightMarkerLook.direction`), drawn under the badge so the two are one shape.
- **Light presets** (`LightPresetDefinition`, `gameSystems/lightPresets/` per system): a collection offers its own (`CollectionSettings.lightPresets`), else its preset's, else the generic four, which are counted in grid cells (`collectionLightPresets`). A preset's distances are in the unit its rules write them in; everything that offers or applies one reads `mapLightPresets` (`lightPresetsOnMap`: converted to what the map's collection measures in as rulebooks convert, a 5e torch is 20/40 ft, 6/12 m, 4/8 squares, and stopped at `maxLightRange`), so the popover, the lighting menu, Carry light and Edit Token give the numbers the range rings and `LightReach` then use. A preset may be a darkness or carry a priority (5e and PF2e Darkness, the generic Darkness; 5e Daylight outranks it), or an `angle` (the bullseye lantern: 53° in 5e, whose cones are as wide as they are long, 90° in PF2e). A light records the preset it came from (`emission.preset`, read with `lightPresetOf`); ids are `<preset key>-<light>` and never change. A token's carried light is edited in Edit Token with the popover's fields (`TokenLightSection`). *Edit Token* (`EditTokenModal`, its sections in `EditTokenSections.tsx` and `TokenLightingFields.tsx`, `edit-token-modal.scss`) is two equal columns of sections under small-caps headings: Token, Resources and Vision on the left, Carried light on the right, as far apart as the body's padding, each as tall as its own content so that switching the light moves nothing on the left. The DOM holds them in that order, which is the tab order and the order of the one column the dialog becomes below 720 px of its own width (a container query on the dialog). Fields stand two to a row (`atlas-edit-token__fields`), a field's reset button lies inside its end, and the popover's rules between its groups are left out there. `tests/gpu/editTokenLayout.gpu.test.ts` measures all of it against the real stylesheet.
- **Light popover and range rings**: store `lightPopover` (UI slice: not saved, not undo-tracked) is the light being edited; `LightPopover` (React, in `UIRoot`) and `LightRangeRings` (PIXI, a `GmOverlays` layer) both read it. `LightInteraction` takes the pointer from `TokenRenderer`'s dispatch after pins and door badges (`setLightHandlers`): a click on a marker opens the popover with any tool, a drag past `LIGHT_DRAG_THRESHOLD` moves the light with the lighting tool only (the history transaction opens when the drag starts), a ring handle resizes bright or dim (`dragRange`: whole game units, tenths with Alt, dim never below bright). A range of 0 has no handle (it would sit on the marker). A light with a beam has arcs for rings, its range handles on the beam's two edges and a third handle `ROTATION_HANDLE_OFFSET` px beyond the dim arc that turns it (`lightRingGeometry.ts` is the one place for where handles are and what is hit; `snapDirection`: 5°, whole degrees with Alt; a cancelled turn puts the rotation back). The popover has Beam and, for a placed light, Direction in one row; Direction is disabled while the light shines all around, so the row never changes height. Typed and dragged ranges stop at `maxLightRange` (`MAX_LIGHT_REACH`, 8,192 world px: the side of the largest map lit at full resolution; 585 ft on a 70 px, 5 ft grid), and a typed range reads a decimal comma where the locale writes one. Only the pointer's release commits a drag: Escape, a pointer cancel, the window losing focus, the popover leaving the light and the players' view cancel it, which puts the light back and leaves no undo step. DOM checks there use Obsidian's `instanceOf`, since a popout window's elements are not `instanceof` this window's classes. It closes the popover on a press anywhere but the popover, a marker or a ring handle; `LightingController` closes it on Escape, when a peek starts when another Obsidian tab becomes active (`active-leaf-change`: a key switches tabs without a press) and when the light, its marker or the GM's view of a loaded scene is gone (`mayEditLight`: delete, undo, scene change, session view, lighting off). The popover is placed with `translate` on the PIXI ticker (`useLightPopoverPosition`; a closing view destroys that ticker before the UI unmounts, so the hook leaves only a ticker the app still has), with the light as its `transform-origin`, so it grows out of the marker; opening another light moves the same popover there. `placeLightPopover` ranks the places around the light (each side, beyond the bright ring or beside the marker): one that fits, covers no ring handle and least of the bright disc, on the roomier side, clear of the scene tabs and the toolbars. It keeps its place while that holds, and the ring and the beam it stays clear of are those it found there, so tuning or turning the light never moves the popover under the pointer; once the Beam or Direction slider is let go, the popover makes way if the beam's handles came to lie under it. The chosen kind chip is ringed in the accent like every chosen control; only its glyph takes the light's colour. Every control writes to the store at once, and a gesture is one undo step (slider, ring and colour picker transactions).
- **Thumbnails** (scene and snapshot cards, `MapThumbnailService`): the off-screen render runs inside `captureSceneFrame` (`pixi/sceneFrameCapture.ts`), which hides pins, hex links and the `GmOverlays` for its duration and calls `SceneLightingView.renderForFrame`, so the composite is held on the frame's own screen-to-world mapping in GM mode (`LightingEngine.renderFrame`) while the layer renders in the tree as on the canvas (PIXI copies any render target into a blend filter's back texture; only the canvas needs the back buffer), and lighting that fails there leaves the thumbnail unlit. A thumbnail is always the GM's picture, also while the canvas is in session view or a peek is held: `renderFrame` holds the composite in GM mode whatever `modeLayer` says, and the capture forces `gmViewLayers` (`TokenRenderer.getGmViewLayers`: every token sprite, hidden ones translucent, and the GM's token UI where it has something to show; `FogOfWarRenderer.getGmViewLayers`), so whatever session view hides through a layer's `visible` or `alpha` shows as in GM view; anything it hides another way must be added there. The layers are put back when the capture returns, so the canvas is in session view again. None is taken on a lost WebGL context or from a store that is not `mapLoaded`.
- **Editing explored memory** (the lighting menu's Explored memory mode, `WallToolSubMode` `'explored-memory'`, its row is disabled unless the scene is lit and remembers: `exploredMemoryEditable`; the menu leaves the mode when that ends): `ExploredBrush` takes every press of the tool in that mode (`LightingModes` routes pointer and keys to it or to the zone editor, so walls and lights take none). A stroke with the brush, the lasso or the rectangle (`ShapeStroke`, `tools/shapeStroke.ts`, the stroke the fog tool draws with too; only the fog's rectangle snaps to the grid) reveals or forgets. What a stroke does, its shape and the brush's size are the tool's choices in the view's store (`exploredBrush`, UI slice: not saved, no undo step), the one place the menu and the brush read them from, so a toolbar built anew shows what the tool does; a change drops the stroke under way. A lasso drawn by hand may cross itself, and PIXI's triangulation of such an outline can fill ground far from it (the long leak fuzz found a room's memory 90 px past its walls), so a lasso is stamped as the pieces its outline fills by the nonzero rule (`filledPieces`, `lighting/polygonFill.ts`: trapezoids between the levels of every corner and crossing), from an outline simplified to 400 corners at most. While the pointer is down the stroke is on the overlay alone; the release applies it through `SceneLightingView.editExplored` to `ExploredMemory.edit`, which stamps the texture sight records into (`ExploredTexture.add` and `erase`, across walls too: the GM decides what is explored) and schedules the usual save. Sight, light and perception never read the memory, so an edit changes only what the players see where they see nothing now. A cancelled stroke (Escape, a cancelled pointer, the window losing focus, another tool or mode, the players' view, the scene unloading) leaves nothing, and the mode takes no input while the canvas shows the players' view. "Mark all areas explored" (offered in the mode) and "Forget explored areas" are edits of the whole map; while the texture is not the memory (its mask still loading) forgetting drops the saved mask at once instead (`ExploredMemory.reset`). *Undo*: the memory is no store state, so the store counts its edits (`exploredEdits`: undo-tracked, never saved, 0 after every load) and an edit is the step that raises the count; undo and redo therefore reach memory edits and store edits in the order they were made, from the same buttons and keys. `ExploredSteps` keeps the texels of each edit's region before and after (`ExploredEditStack` in `lighting/exploredEdits.ts`: read from the texture at its own size with `readCoverage`, never through the saved image, run-length packed, as many steps as `HISTORY_LIMIT`), and when the count moves without an edit of its own (`ExploredMemory.follow`) it takes the steps between back or forth by one rule (`travelledCoverage`). Only the texels the step changed are written, never the rest of its rectangle: what sight recorded beside a stroke stays. Where a step gives memory (a Forget undone, a Reveal redone) a texel never ends with less than it holds. Where it takes memory away (a Reveal undone, a Forget redone) a texel the party has really seen since the step was first made keeps it: undo and redo never remove what was seen. To know that, while steps exist, sight's records are stamped into a second texture of the memory's size at the serial of the newest edit (`ExploredSteps.sightRecorded`, `ExploredTexture.add(shapes, level)`), so a texel reads "last seen while edit n was the newest" and `seen >= step.serial` is "seen since"; a texel sight covered only in part holds less and may be taken. A serial is a byte: after 255 edits in one stay the older steps can no longer be undone and leave the history. The steps last while the scene stays loaded: they go when it unloads, when the texture is replaced (the map changed size) or the engine's view goes, and then they leave the history with them (`forgetExploredEdits`, `stores/exploredEditHistory.ts`), and a tab's cached history is kept without them (`withoutExploredEdits` in `AtlasView.saveTemporalState`), so undo never meets a step that does nothing. The GM's canvas shows the memory only in the mode: an undo or redo of a memory edit outside it tells the GM with a notice (`ExploredMemoryWatcher.memoryTravelled`). *Overlay*: `ExploredOverlay`, the `exploredMemory` layer of `GmOverlays`, shows the memory's own texture in the theme's accent and the stroke under way as it will land (a brush stroke from the same points the stamp keeps, `countsInBrushStroke`), in one layer an `AlphaFilter` fades as a whole (a stroke that crosses itself or the memory is no darker; a forget is drawn into it with `erase`), with the fog tool's brush ring; `LightingRenderer` hands it each new texture before the last is destroyed (`exploredWatcher`). *Players' picture*: the composite is unchanged and reads the memory through `exploredAt`'s wall-aware blur, so a room revealed along its walls shows nowhere past them, by the bound sight's own memory is held to, and a dab across a wall shows on both sides and nowhere beyond itself (`leakFuzzMemoryBrush.gpu.test.ts`, run with the leak fuzz). An eraser with soft edges takes of an edge texel the share it covers, so forgetting exactly what was revealed leaves a trace on the edge (at most a quarter of a texel); undo is what takes an edit back exactly.
- **Walls**: never snapped to the grid. A chain or freehand stroke is one undo step through `WallDrawingSession` (cancelling leaves no step); splits and bulk edits run in `runHistoryTransaction`. Walls join at their ends (`pixi/lighting/wallEnds.ts`): a click in place on a wall end starts a chain there (continuing the chain of the one wall ending there), a chain under way takes every press and lands its corners on wall ends within 10 screen px, and a dragged joint lands on one too (never where its walls' far ends are); Alt places freely. Ends within 2 px are one joint and move together. Doors are placed in the wall under the pointer, one grid cell wide (`placeDoor`, `DoorPlacement`); `wallJoints.ts` removes a point (two walls of one type become one) and a door (rejoining the straight walls beside it). Doors toggle from their badges with any tool (`DoorIcons`, dispatched from `TokenRenderer`), also from the badges the players' view shows (Player frame and session view, above). A door may be locked (`WallSegment.locked`, set only through the store's `setDoorLocked`, which also closes it; `toggleDoor` leaves a locked door shut): a GM aid without a rule of its own, light and sight read only `closed`. Its badge shows the GM a padlock (the players' badge looks closed) and, clicked, shakes for a moment instead of opening (a tint where motion is reduced; `DoorIcons.refusal`), read from the canvas' own document: a popout has its own). A map file's `locked` counts only where it is `true` (`wallsFromFile`). A right-click on a badge opens the door's menu with any tool, in GM view only (`doorMenuEntries`: open or close, lock or unlock; `TokenRenderer.setDoorMenuHandlers`), and the lighting tool's wall menu has the same entries for a selected door.
- **Canvas renderer**: `CanvasLightingFallback` keeps the map black outside sight in the player view (fails closed, unless the scene has token vision off) without light, shadows or memory; it also stands in on a GPU renderer whose device cannot run the engine (above). PIXI falls back to Canvas by itself only when WebGL is missing at its first check, whose answer it keeps, so `PixiAppManager` asks before every start (`webglAvailable`) and starts the Canvas renderer directly when WebGL is gone; should WebGL throw all the same, it retries once with Canvas on a new canvas (that failed renderer cannot be reached to destroy it). It opens holes only for regions that show the map and for footprints, works nothing out for store changes sight does not read, keeps its sight the same object while the regions are the same (so `PerceptionMemo` holds), and ignores `litThreshold` (everything in sight counts as lit, `FULL_DAYLIGHT`, as a dark scene would otherwise hide every token without its lights) and the explored and unexplored colours.

## Loading and skeletons
What is loading shows a skeleton in its own shape, and loading never costs the UI a frame.

- **Primitives** (`packages/components/primitives/`): `Skeleton` (shapes `block`, `circle`, `pill`, `text`: a text bar stands in a line of the real element, so it takes the font's height) and `SkeletonGroup` (a surface that is loading; `label` says what for screen readers, left out where a progress line beside it does). Styles in `skeleton.scss`, mixins in `styles/_skeleton.scss`. A skeleton reuses the classes of what it stands for (`ContentSkeleton` builds real `.atlas-asset-card`s), so content replaces it without a shift; `tests/gpu/assetManagerSkeleton.gpu.test.ts` holds cards to the place of their placeholders.
- **Motion is compositor-only**: skeletons animate `transform` and `opacity`, never a background (the same rule as `LoadingSpinner`), so they keep moving while the main thread loads; the GPU test fails on any other animated property. A group has one sheen: a band of the surface's own colour (`--atlas-skeleton-surface`, default `--background-primary`; set it where a group sits on another surface, as the sidebar does) moved by one transform, which fades the shapes it passes and can not be seen between them. A single late piece inside real content breathes instead (`live`, `.atlas-image-placeholder`), in step with every other one (`skeletonPhaseStyle`). Reduced motion: no sheen, one slow breath.
- **When a skeleton shows** (`useLoadingReveal`): a load that replaces content shows its skeleton only once it has lasted `SKELETON_DELAY_MS`, and then for at least `SKELETON_MIN_VISIBLE_MS`; until then keep what was there (`useHeldWhile` in `AssetManager`: a quick tab or collection change swaps the panes once). A load that runs at mount (opening the manager) has nothing to keep: its skeleton shows from the first frame and leaves when the load ends. Never an empty state or an empty pane for content that is not loaded. The skeleton stands in the pane its content will have (`Content`), so the cards take the place of their placeholders without a transition between them.
- **The asset grid while it scrolls** (`VirtualAssetGrid`): scrolling is drawn before the grid renders again, so the rows around the mounted ones show placeholders (`gridSkeleton.ts`: one element per stretch, a tint masked with a card's shape measured from a mounted card and repeated per cell, up to `REACH_PX` away; static, so it only scrolls). A card that scrolls out of the mounted rows leaves at once; only a card the list lost fades (`cellVariants`, told apart by the presence's `custom`): fading scrolled cards kept every card passed mounted, 513 where 63 were needed, and each scroll step rendered them all. `presenceAffectsLayout` is off, or every render sends a context change through the subtree of every card. Card images load with their card, not lazily: rows are mounted ahead of the view, so their art is there when they scroll in. Measure scrolling with a CPU profile in the browser tests (`cdp()` from `vitest/browser`) and frame times in the live app before changing this.
- **Asset manager data** (`hooks/useAssetData.ts`): `assetsLoading` and `tagsLoading` say that what is held belongs to another selection; `assetCounts` is null until counted. A load overtaken by a later one is dropped. Reloads go through `reconcileAssets`, which keeps the object of every unchanged asset (cards are memoised on it) and the list itself when nothing changed. Thumbnails arrive as patches (`withThumbnails`), never as a reload.
- **Images** (`RevealImage`, `useImageReveal`; `TokenPortrait` with `reveal`): a placeholder holds the place until the image can be painted, then it fades in. An image this window has shown before mounts shown, so scrolling a virtual list back neither flashes nor fades.
- **Thumbnails** (`AssetThumbnailService`): a token or map card without a thumbnail shows a placeholder while one is made (`stateOf`, `Asset.thumbnailPending`) and the full image only when none could be made; decoding a full map for a card costs hundreds of megabytes. Cards on screen report themselves (`useArtPriority`, `prioritize`), so theirs are made first. Listeners hear of thumbnails soon after they are written (`ThumbnailUpdate`, with `thumbnailPath: null` for a failure); the index is saved for them at most every few seconds, since each save writes the whole index.
- **Long loops on the main thread** await `workSlices()` (`utils/workSlices.ts`) between units. A loop that only awaits work already done (cached reads, values in memory) continues in microtasks, which run before the browser may paint: `CreatureIndex`, `unparsedStatblockNotes` and the statblock import scan froze the window on large libraries that way.

## Image imports
- **Convert through `src/app/imageProcessing/`**, never on the main thread: `optimizeImage`, `renderFramedImage` and `renderThumbnail` run in `ImageWorkerPool`, dedicated workers (bundled inline with Vite's `?worker&inline`) that decode with `createImageBitmap`, draw on an `OffscreenCanvas` and encode WebP with `convertToBlob`. Browsers encode on the CPU only, so speed comes from parallel workers, one decode per image and no intermediate formats. The pool is disposed in `onunload` and stops idle workers.
- **Memory budget**: each job's cost is estimated from the image header (`imageDimensions`: PNG, JPEG, WebP, GIF, BMP; twice the decoded size), and jobs run together only while their costs fit 1 GiB. Formats it cannot read (SVG, AVIF) and images larger than the budget run alone. Conversions started ahead of time (creator previews) pass `background`, so work someone waits for, such as the crops at save, starts first.
- One job returns everything an import writes: the image, its thumbnail (`THUMBNAIL_SPEC`, only requested where that result is saved) and, for map cards, a small preview. Store it with `AssetThumbnailService.tryThumbnailForImage`, which renders one from the saved image when none came with it. Creator cards show only converted images, never the upload.
- Token art is converted in `token-creator/tokenImages.ts` for both the creator and `StatblockTokenImportService` (the "Create token from statblock image" command): framed tokens are a `frame` job placed by `tokenCropPlacement` (the crop editor's numbers), unframed ones fit the token preset. Batch imports start every conversion at once and register assets in order.
- Downscaling draws with `imageSmoothingQuality = 'high'` after halving to less than four times the target; a single draw over a larger reduction aliases. A WebP source that needs no scaling is kept byte for byte. SVG (which workers cannot decode) is rasterized on the main thread and transferred as an `ImageBitmap`. A vector has no pixels of its own, so it is drawn at the size the job asks for (`vectorRasterSize`): an SVG map fills the map preset, never a smaller raster that is scaled up. These rasters run one at a time, each until its worker is done (`afterEarlierRasters`), because their bitmaps wait outside the pool's memory budget.
- **Maps keep at most 8192 px per side** (`IMAGE_PRESETS.map`), because a map is one GPU texture. A larger upload loses pixels, which the job reports (`ImageJobResult.scaledDown`) and the creator's map card shows. WebP quality is not what blurs a map: within the limit an import is visually unchanged.

## Universal VTT import
Maps exported with their walls, doors and lights: `.dd2vtt`, `.uvtt`, `.df2vtt` (Dungeondraft, DungeonFog, Dungeon Alchemist). One JSON file holds the image as base64 and every position in grid cells, counted from `resolution.map_origin`. Code in `src/app/import/uvtt/`.

- **Parts**: `parseUvtt(text)` (pure; a typed `UvttMap` or a problem sentence, never throws), `uvttToScene(map, { cellSize, unit })` (pure), `importUvttFile` (the vault; never throws), `runUvttImport` (the image workers and the notices: one while a file runs, one with its counts or the reason it was refused).
- **Where it enters** (`asset-manager/hooks/useUvttImport.ts`, called from `ModalLayer`): the map creator hands the map files among picked or dropped files to `ImportMaps`, and map files dropped anywhere on the asset manager's window are imported into the selected collection. The drop is heard on the document in the capture phase, since a folder tile takes every drop on it. A drag names no files, so drag-over accepts files of an unknown type (`type === ''`), which is what the three extensions report. The scene opens only for the asset manager that started the import: still open, no other dialog open, and no images waiting in the map creator; otherwise the scene is only added.
- **The file is untrusted.** Only an object's own fields are read (`own`). What places things is strict: map size, origin, every position, a light's range, the image; anything wrong there refuses the file with a sentence naming the field. What only colours or switches falls back to its default (light colour white, intensity 1, no ambient, `closed` and `baked_lighting` read by `readFlag`), and fields the import has no use for (`format`, `pixels_per_grid`, a door's rotation) are not looked at. The image's type is read from its bytes, never from what the file claims. `UVTT_LIMITS`: 150 MB, 20,000 wall segments and doors (counted before their points are read), 2,000 lights, 4,096 cells a side, and as many image pixels as the image workers' memory budget holds decoded.
- **Grid**: the image keeps its pixels at the origin and the file's grid becomes the scene's: `grid.size` is the saved image's width divided by `map_size.x` (`uvttCellSize`), so a map scaled down to 8192 px still fits; the offsets come from a fractional origin; no auto-detect. Cells must be square within 2 px and at least 10 px wide. A position `p` lies at `(p - origin) * cellSize` world pixels, unrounded.
- **What is placed** lies on the image or within one cell of it (`placeableRect`): a wall is cut where it leaves, and a wall, door or light outside is left out (counted in the debug log only). A file with nothing on its image is refused, as is one whose wall ends crowd (`wallsCrowd`): `sealWalls` builds a bridge per pair of wall ends within the seal tolerance, so thousands of ends in one spot stall the scene.
- **Mapping**: each wall line and object outline gives one solid segment per pair of points, with one `chainId` per line. A closed portal is a closed door between its two ends; an open portal is a window in Dungeondraft (it stops movement, not light or sight) and is skipped. A light ends at its range in cells times the collection's `unitDistance` (band collections alike), capped at `maxLightRange`, and is bright to half of that; it is a `custom` light, and one without range is skipped. `baked_lighting` imports the lights switched off (`hidden`) on a scene in daylight. Ambient light is the Rec. 709 luma of `ambient_light`, daylight when the file names none. Dynamic lighting is on.
- **One step** (`writeImport`): the image, its thumbnail, the `.atlasmap` (built by `newSceneFile`, which the New scene dialog shares), both record files and one `commitAssetTransfer` happen inside `assetService.runExclusive`, where the collection is read again, and a failure takes every file back before the lock is released. The map and the scene share a name; a taken name is numbered.
- **Tests**: `tests/unit/uvtt*.test.ts(x)` with hand-written files (`tests/fixtures/uvttFiles.ts`); `tests/gpu/uvttImport.gpu.test.ts` runs the import with the real image workers.
